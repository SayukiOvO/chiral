# 原始模板候选投影验证（2026-09-29）

## 结论

完整配置回读和基础授权切换可行，但该候选方案仍未满足计费等价性。加强后的第二轮实验
明确复现冷启动漏计，以及全新 `level:3` 用户配置回读正确、能传输正文却没有用户计数的
情况。两轮均整体 FAIL；不采纳为生产投影方案，不启用 ACTIVE。

## 范围

通过官方未修改的 3x-ui HTTP API，测试“原始模板承载真实配置，停用的受管对象仅建立
计费索引”的候选方案。它不是已采用的生产架构，也没有接入 ACTIVE provider。

只运行本机 Docker 新建的空实例，无外部网络、宿主机端口、生产挂载或生产凭证，没有
连接 Turin。官方镜像 digest 为
`ghcr.io/mhsanaei/3x-ui@sha256:e0f90c10902e0e74f947d5a9efe017b273804477430233bbfc4918542ffe366c`，
实际 Linux/amd64 镜像为
`sha256:be0af3a71e948bab24852b5dc571fd9835834847f086a84b1c4eb5932dd0fe50`。
这是本次可复现验收输入，不是固定产品版本策略。

完整比较包含 api、stats、policy、路由与 client 字段，不按已知失败字段设置例外。
受管 inbound 及其 metadata client 永久停用，额度、到期、续期均为零；实际授权只由
原始模板决定。测试流量经独立临时客户端穿过回环 VLESS 入站，下载正文校验 SHA-256，
计费读取只使用官方 HTTP，不读取 Xray 管理接口。

## 首轮取证

目录：`/private/tmp/chiral-raw-projection-20260929-01`。
测试 `TestLive3XUIRawProjectionContract` 整体 FAIL，94.25 秒；测试、Docker 执行和运行器
均返回退出码 1，没有 SKIP。这是明确的等价性失败，不是测试没有执行。

- 原始模板、最终配置完整比较，以及 client `level:3` 回读通过。
- 冷启动真实上传 32768 字节、下载 524288 字节通过，但四十秒内用户累计仍为 0：FAIL。
- 第二笔真实请求用户增量为上传 32988、下载 524510 字节：PASS。
- 移除、恢复 client 后，新连接分别失败、成功；恢复后的同 email 用户流量仍不增加：FAIL。
- 清理确认 `raw_template_restored=true`、`metadata_removed=true`、
  `assembled_config_unchanged=true`。本轮三个容器停止，数据卷与私有日志保留。

复核发现首轮的反向测试尚缺有效控制用户，而且“移除后恢复同 email”的计费不能单独
证明纯热新增语义：默认停用策略可能触发重启，旧计数或迟到采样也可能干扰。因此不能将
首轮局部成功表述为完整授权或热更新验收。后续测试应保留用户 A，新增全新凭证与 email B，
确认 B 初始计数为零后再验证热新增；撤销 B 时还必须确认同一入站的 A 仍可用。

| 独立检查 | 实际结果 |
| --- | --- |
| 完整模板及最终配置回读 | PASS，保留 `level:3`，不忽略统计或路由字段 |
| 用户 A 冷启动首笔真实传输 | 正文通过；四十秒内用户计数仍为 0/0，计费 FAIL |
| 用户 A 后续传输 | PASS，用户增量上传 32988、下载 524510 字节 |

| 移除 B、保留 A | PASS，B 新连接被拒；A 在反向窗口前后均能取得完整正文 |
| 恢复 B | 新连接及正文 PASS；再次等待四十秒，B 计数仍为 0/0，计费 FAIL |
| 清理和恢复 | PASS，原模板、最终配置和原测试 URL 恢复，metadata 全部移除 |

两个用户的 metadata 在主要阶段均保持停用、零额度／到期／续期；创建 B 的 metadata 后
还确认原始运行配置未变。反向测试先完成本地 SOCKS5 握手；任何源站命中或完整 HTTP
响应都判为撤权失败，父级超时、测试进程退出或本地代理未就绪不能当作通过。

上述结果与源码中的热更新 Level 缺失一致，但未通过 HTTP 直接读取运行时 Level；没有
监测服务端 PID，因此“热新增”只描述仅追加 client 的请求差异，不证明上游内部绝未重启。
这也不验证已有长连接是否中断。实验不能被外推为全部协议、全部字段或生产配置等价。

本轮三个容器均停止，容器、卷和私有日志保留；未删除现场，未操作任何现有节点。

## 已确认的上游行为边界

源码依据为官方提交 `7ef22f94c950ff09f0870e2295fa65ad5968742c`，未修改其源码：

- `internal/web/service/inbound_traffic.go` 按 tag/email 更新计数时不筛选 Enable，支持
  停用对象作为计费索引的局部可行性，但不解决首次采样损失。
- `internal/xray/hot_diff.go` 计算 raw client 热差异，而 `internal/xray/api.go` 的
  AddUser 构造运行时 User 时不设置 Level。数据库模板回读保留字段，不等于运行态已采用。
- `internal/web/service/inbound.go` 删除停用 inbound 仍会移除同 tag 路由引用；清理必须
  先移除实验运行配置，再删元数据，最后再次恢复完整快照并比较。
- `getConfigJson` 的配置组装也可能执行生命周期维护，不能将所有读取一概称为无副作用。

此实验不覆盖完整生产 Profile、所有客户端订阅、实时在线完整快照、真实内核下载或
生产切换。继续保持 ACTIVE 关闭，不能用第二笔计费成功抵消首次漏计。
