两个观察阶段均出现累计计数增长。普通 `/clients/traffic/{email}` 查询在删除后返回 API
拒绝，不能用它推断本机账务行被删除，更不能改用可能含主面板汇总的数据计费。

这是有界观察，不是最终结算证明、全协议兼容保证、任意字段保真或 Agent→Core 端到端
验收。没有启用可写 3x-ui Runtime 或 ACTIVE，也没有访问 Turin、生产配置、数据库或订阅。

## 验证方法

所有服务端控制均通过官方 HTTP。先要求空对象集合、API-only 原模板及已运行的同一实例。
全量读取官方设置，只改变 `restartXrayOnClientDisable=false`，完整语义回读；拒绝已有
敏感配置和异常字段类型。结束时仅在当前设置仍等于本次候选时恢复原快照并再次完整回读。
不调用 Panel 重启接口，不对未知写入盲重试，不把此测试用全量设置助手加入生产路径。

模板只建立自有路由、回环重定向出站和 level 0 统计策略；两个账户都是同一受管 inbound
中的真实 managed client，不是原始模板中的账户或停用的占位元数据。另起的单个私有 Xray
进程仅是**数据面测试客户端**，有两个独立 SOCKS 入站和凭证出站，显式禁用 mux。它不访问
Xray 管理 API，不控制官方服务端进程、文件或二进制。

每条流仅建立一次 HTTP 响应。源站收到命令后才生成包含账号角色及序号的 64 KiB 块，读端
必须逐字节收到，不能以源站写成功或缓存的旧字节代替。新连接检查使用新传输连接；撤权后
重复负向尝试，保持本地 SOCKS 可用，并用另一账号的正向请求排除整体服务故障。首次负向
检查后冻结的源站计数在 500 ms 静默窗口、后续流量、删除及最终关闭阶段均不得增加。

先观察两账号计数为正，再安排 12 秒不产生新数据的读回阶段降低基线归因噪声。随后停用，
观察 20 秒；再保留统计删除，观察 15 秒。静默或稳定计数都不被当作上游结算屏障。

采集，更没有估算、补写冷启动首次基线缺口。运行器 PASS 检查实验完整性，具体“行仍存在”
及“计数增长”结论来自上述实际字段，而非 PASS 本身。

日志明确保留 `final_settlement_verified=false`、`core_integration_verified=false`、
`arbitrary_field_preservation_verified=false`。上游没有同步 flush 或最终序号，本实验没有
验证删除 inbound、清空统计、数据库恢复、重启后的尾部保留，也没有授权任何自动清理策略。
