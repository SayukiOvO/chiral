# 私有探针预热与首笔计费验证（2026-09-29）

## 验收范围

本实验只回答一个问题：全新官方实例先仅开放私有探针，确认其流量被官方计入后，再增加
完整的新用户入站，是否能计入该用户的第一笔流量。它不是生产启动流程，也不覆盖
Panel／采集任务重建、已有入站内热增用户、完整在线快照或整体迁移。

全程在本机创建空 Docker 实例，`network=none`，无宿主机端口、生产挂载或外部访问。
不访问 Turin，不修改 3x-ui，不使用测试程序启动 Xray 或调用 Xray 管理接口；所有控制、
探测和统计均走官方 HTTP。源站只监听同一命名空间的回环地址。

## 输入与判据

- 运行器：`write_contract.py --suite billing-bootstrap`。
- 测试：`TestLive3XUIBillingBootstrapContract`。
- 官方镜像：`ghcr.io/mhsanaei/3x-ui@sha256:e0f90c10902e0e74f947d5a9efe017b273804477430233bbfc4918542ffe366c`。
- Linux/amd64 镜像：`sha256:be0af3a71e948bab24852b5dc571fd9835834847f086a84b1c4eb5932dd0fe50`。
- 源码依据：原版 v3.8.5，`7ef22f94c950ff09f0870e2295fa65ad5968742c`，未改动。

私有探针和模拟用户各有独立 tag、端口、UUID、email；受管索引永久停用，额度、到期及
续期字段为零，真实授权只存在于完整原始模板。测试使用 `level:3`，且 level 0 的用户字节
统计关闭、level 3 开启，防止配置回读正确但运行时 Level 丢失而被忽略。

1. 仅开放私有探针，最多发送六次，每次有界观察官方累计值。实际计入后停止探针流量，
   再连续观察至少六秒稳定值；固定等待本身不能证明预热。
2. 保留探针和全局策略，复用其专用出站，只增加完整用户入站及专用路由。
3. 新用户计数必须从零开始；只发送一次 `real` 探测，不发送 readiness 或重试请求。
4. 源站须仅命中一次、成功写出 51,200 字节，官方响应成功；用户下行增量至少覆盖正文，
   上下行均不得超过单次请求的有限额外开销；探针账户保持不变。
5. 完整回读 stored template 与 assembled config，最后分别恢复、比较各自原始快照。
   先还原运行模板，再删除确定归属的停用元数据，最后再次还原，防止删除接口重写路由。

官方探测最多读取 256 KiB，此正文小于其上限。但上游忽略读取正文的错误，因此这项证据
是源站成功写出、官方状态及持久化计数的组合，不是客户端逐字节正文验收。公开字面 IP
只是隔离路由的逻辑目标，不证明公网连通。

## 结果

首轮 `/private/tmp/chiral-billing-bootstrap-20260929-01`：FAIL，退出码 1，0.12 秒。
测试在发送任何探针前错误地用 assembled config 比较原始 stored template；两者初始
统计字段确实不同。已修正为各自完整快照比较，没有忽略差异字段。首轮清理也受该错误
阻断，不能宣称完整恢复；其停用元数据、容器和卷全部保留，容器已停止，不复用该实例。

第二轮 `/private/tmp/chiral-billing-bootstrap-20260929-02`：PASS，30.04 秒，无 SKIP；
测试、Docker 执行和运行器均退出 0。

| 观察 | 结果 |
| --- | --- |
| 私有探针第 1、2 次观察 | HTTP 计费仍为零；不视为预热成功 |
| 私有探针第 3 次观察 | 上行 129、下行 51,305 字节，之后稳定 |
| 新用户第一次、唯一一次请求 | 上行 129、下行 51,305 字节；正文 51,200 字节 |
| 账户隔离 | 用户请求未改变探针计数 |
| 完整恢复 | 原模板、原 URL、最终配置、空对象列表和运行身份全部确认 |

第三轮 `/private/tmp/chiral-billing-bootstrap-20260929-03` 使用最终测试程序及另一新实例：
PASS，23.99 秒，三个执行退出码均为 0，无 SKIP。第 2 次私有探针已出现计费；随后新用户
唯一请求仍计入上行 129、下行 51,305 字节，独立账户及完整恢复均通过。两次成功需要的
私有探针次数不同，说明不能用固定请求次数代替实际计费回读。

共享源站夹具修改后，原 HTTP 探测与三个更新故障恢复场景也在另一个新实例回归：
`/private/tmp/chiral-http-probe-20260929-03`，PASS，35.09 秒，各执行退出码 0，无 SKIP，
完整清理通过。安装返回仍为注入，没有真实下载。另有全量 Go 回归、静态检查、Core/Agent
构建及 53 项运行器安全测试通过；新增配置生成回归确认全局策略、独立用户和路由保持。
本轮四套实验的十二个容器均已停止并保留，未删除卷；首轮保留失败现场，其余三套确认
模板和对象恢复。容器停止状态另经精确 ID 的只读检查核实。

## 仍然不成立的推论

- 成功只能支持受控的首次开放组合，不是可持久宣称的“采集器已预热”能力。官方 HTTP
  没有提供可用于无竞争判断的采集任务代次标识；`appStats.uptime` 实际来自 Xray 进程，
  不能当作 Panel／采集对象的启动时间。
- Panel／采集对象重建时已有用户可能立即恢复，先预热再开放的前提不再成立。
- 完整新入站使用的原生路径不同于同入站热增用户，不能抵消既有实验的 Level 丢失证据。
- 不证明保留所有现有连接、计费周期切换无漏记、完整在线快照或生产订阅等价性。

因此没有接入 ACTIVE provider 或生产启动逻辑，其他未通过门槛继续保留。
