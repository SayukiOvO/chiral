## 出网与隔离要求

普通独立 bridge 不足以证明实验无法访问宿主机、LAN 或生产地址：它仍提供出站网络。
仅设置 `internal` 也不足以隔离桥地址上的宿主服务。Docker 官方说明，internal 网络配合
`gateway_mode_ipv4=isolated` 时才不为桥分配地址；相关行为仍须在实际运行器中核验，不能
只检查配置文件。[Docker 官方网络说明](https://docs.docker.com/engine/network/port-publishing/)

独立实验运行器采用以下拓扑：

1. 3x-ui 与测试器仅加入本轮新建的 internal、isolated gateway 网络；关闭 IPv6，不配置
   宿主端口，不使用宿主网络、既有网络、Docker socket、生产目录或生产凭证。
2. 独立的通用 CONNECT 代理连接实验内网与专用出网网络。代理只负责限制网络目标，不
   实现 3x-ui 接口，不变更控制响应，不提供内核缓存，不解密 TLS，不替代官方下载。
   它不是增强 fork 或兼容服务，不得扩展为这些用途。
3. 3x-ui 使用显式 `HTTPS_PROXY` 指向实验代理；清除继承的其他代理配置，`NO_PROXY`
   只涵盖实验回环控制接口。Panel outbound 保持未配置。
4. 代理只接受精确允许域名的 `CONNECT`，端口限于 `443`。初始待验证名单为
   `api.github.com`、`github.com`、`release-assets.githubusercontent.com`；禁止通配域名、
   任意 IP 字面目标、其他端口及普通 HTTP 转发。遇到名单外重定向时失败，不自动扩大权限。
5. 目标解析与拨号必须使用同一份已经核验的公网地址，拒绝回环、私网、链路本地、保留
   地址及其他非公网地址，防止二次解析绕过限制。执行前核对实际允许地址；TLS 证书验证
   保持开启。域名允许名单不是任意公网访问许可。
6. 代理不启用 IP 转发，移除 capabilities，使用 `no-new-privileges`，配置资源上限和
   有界超时；除专用实验配置外无宿主挂载。仅记录目标域名、允许或拒绝以及字节计数，
   不输出凭证、完整环境、TLS 内容或下载重定向查询参数。
7. 对网络 ID、归属标签、gateway 模式、容器路由、端口和全部挂载进行实际检查。负向
   验证使用本轮自建陷阱端点或代理拒绝记录，不主动探测真实 LAN、Turin 或生产服务。

**不得使用正在被更新的 Xray 作为下载代理。** 官方更新在下载前停止该进程；依赖它的
SOCKS 路径会随之不可用。使用独立实验代理是为了隔离和保持下载路径，不改变更新语义。

运行器还提供默认关闭且互斥的实验 DNS 选项。`--proxy-dns 1.1.1.1` 只设置新建代理容器的
DNS；第 04 次仍得到 `dns_non_public`，不构成解析成功证据。`--proxy-dns-over-tls` 固定直连
`1.1.1.1:853`，SNI 为 `one.one.one.one`，最低 TLS 1.2，验证证书且不回退明文 DNS；运行器
仅把该代理容器的显式 DNS 设为 `127.0.0.1`，不改变宿主、Docker daemon、应用容器、3x-ui、
全局或生产 DNS。DoT 只是本机实验出网选项，不是 Chiral 产品运行时设计。

更严格的备选是保留 3x-ui 的 `network=none`，通过专用 Unix socket 卷和回环 TCP 转发
连接受限出网代理。该方案需要额外辅助进程与安全验证，当前没有实现，也不作为既有运行器
已经具有的能力。

## 版本选择与持久化反例

截至核验时，[官方发布页](https://github.com/XTLS/Xray-core/releases) 列出了 `v26.9.8`
与 `v26.9.9`，后者与上述镜像的内置版本相同。执行时必须由原版 HTTP 版本目录重新确认
两者存在，并将精确标签写入本轮记录；不能使用 `latest`，不能自动换成其他版本。

**仅在更新至 `26.9.9` 后重建，再看到 `26.9.9`，不能证明内核卷持久化正确。** 如果遗漏
`/app/bin` 挂载，新容器仍会从镜像取得同一版本，形成假阳性。因此采用两个阶段：

1. 从新实例通过官方 HTTP 真正下载并切换到 `v26.9.8`，作为实验基线。这是普通在线版本
   切换，不是离线回滚，不复用旧二进制缓存。
2. 将该实例重建为新容器 ID，复用本轮原有的 `/etc/x-ui` 与 `/app/bin` 专用卷，确认仍是
   `26.9.8`，而不是镜像默认的 `26.9.9`。
3. 再由候选协调器执行实际 `26.9.8 → v26.9.9` 在线更新，随后再次重建并验收。

`/app/bin` 必须使用本轮新建的完整可写命名卷。首次创建允许 Docker 将镜像初始内容复制
进去；不得使用空目录 bind mount 或 `nocopy`。Core、Agent 和测试器不得挂载该内核卷，
不得自行写入、替换或运行其中的二进制。持久化检查通过 Docker 的限定元数据与官方 HTTP
状态完成，内核安装全部由 3x-ui 执行。

## 执行与验收步骤

1. 建立新实例和归属清晰的私有记录，确认空 managed 对象、初始模板、实例 GUID、Panel
   版本、运行内核、实时 OpenAPI 与专用网络边界。只创建本轮随机夹具，不导入生产数据。
2. 通过 HTTP 建立回环代理路径及独立测试源站，保存完整配置、实验用户凭证和验证摘要；
   更新前必须证明使用这些凭证可以通过真实代理路径取得预期 HTTP 响应。
3. 按上一节执行 `v26.9.8` 基线安装与第一次重建。要求明确安装成功、目标运行版本、相同
   GUID、完整模板和凭证保持，以及重建后的真实 HTTP 数据探针通过。
4. 使用 `XrayUpdates` 候选协调器执行 `v26.9.9` 更新。安装请求必须走原版真实 HTTP
   传输，不能注入目录、安装返回、下载归档或校验文件。请求预算应覆盖上游有界下载时间，
   同时保留每个操作的确定 ID、版本前置条件和持久化派发记录。
5. 同时验证安装明确成功、实例未替换、运行目标版本、配置与凭证没有漂移，以及官方 HTTP
   数据探针成功。仅进程存活、状态接口正常或 HTTP 安装返回成功，都不是充分验收。
6. 验证同操作 ID 重放、协调器关闭重开后不会重复派发安装。再重建应用容器，核对新的
   容器 ID、原卷来源、实例 GUID、目标版本、配置、凭证和代理路径。
7. 保存确定的测试成功标志、测试进程与运行器退出码、网络及挂载检查、前后状态和脱敏
   证据。仅停止本轮拥有的容器，保留卷及私有证据，不执行广域清理。

应用容器重建必须由宿主运行器按本轮资源记录执行，测试容器不得持有 Docker socket。
可采用分阶段测试与独立私有测试状态卷，跨阶段保留随机夹具身份和更新日志；这些数据
不得进入 Git，也不能通过重建或删除记录解除更新限制。

## 失败及未知结果

- 下载明确失败与服务是否恢复是两个结果。仅在既有协调器要求的同实例、持续停止及能力
  检查满足时，允许其进行一次官方恢复重启，并验证真实数据路径；不得称为离线旧内核回滚。
- **未收到安装结果时不得重装或立即重启。** 请求超时不证明上游下载停止，状态显示目标
  版本也不证明这次安装已经有明确终态。保留 unknown 和派发记录，仅进行有界只读核对。
- 官方提交 `7ef22f94c950ff09f0870e2295fa65ad5968742c` 的 `internal/web/web.go` 第 651 行
  将 Web `WriteTimeout` 设为 30 秒，而 `internal/web/service/server.go` 的 `downloadXRay`
  HTTP client 为 60 秒。第 05 次脱敏上游日志出现下载 `context deadline exceeded`；明确失败
  可能已经发生，但 handler 可能来不及把终态写回。因此 Chiral 必须保留 unknown，不得推断安装
  已停止、立即重试或触发恢复写入。
- 恢复回应丢失时也不得重复派发。协调器重启、容器重建或测试阶段切换都不能擦除持久化
  日志与已有未知状态。
- 失败现场应保留。仅在授权范围内停止本轮实验资源；不能以完成清理为理由操作既有服务，
  也不能把未完成的下载或健康检查记作 PASS。

本计划即使通过，也只补齐普通在线更新与实验重建的证据，不覆盖生产迁移、全部订阅等价、
在线绝对快照、计费完整性或任意配置的安全应用。相关门槛仍须独立验收。
