# 用户端门户与在线地址记录（M5）

> **状态：已实现（M5）。** 本文记录实际做出来的东西与背后的取舍，不是提案。
> 与 [`user-management.md`](user-management.md) 的分工：那份讲**代理用户**（配额、凭证、订阅），本文讲**登录身份**（注册、会话、门户能看到什么）。

## 1. 是什么

面板从此有两类主体：

- **管理员（运维）** —— 管机队。账号在 `admins`，会话在 `admin_sessions`，走 `/api/*`，界面在 `/admin/`。
- **端用户（订阅者）** —— 只看自己。登录身份在 `user_accounts`，会话在 `portal_sessions`，走 `/api/portal/*`，界面在 `/`。

端用户能看到：账户状态（已用流量 / 配额 / 到期）、订阅链接（分客户端格式、二维码）、**他有权限的**线路及其可用性与自己在该线路上过去 24 小时的流量、以及（功能开启时）自己的来源地址。

整套门户由 `CHIRAL_PORTAL_MODE` 控制，默认 `off`——此时 `/api/portal/*` 整棵路由树根本不注册。

## 2. 边界靠构造，不靠小心

这是本次最要紧的部分。「客户的 token 不能碰到运维的路由」如果只靠代码审查保证，迟早会被一次手滑破掉，所以做成四层，按抗误改能力排序：

1. **令牌解析物理隔离**。门户 token 只查 `portal_sessions`，而 `AdminBySession` 是 `JOIN admins ON admin_id`——门户 token **不可能**解析成管理员身份。这个保证是一个表名，不是某人要记得写的 WHERE 子句。

2. **处理器签名不统一**。门户 handler 多收一个 `portal.Identity` 参数：

   ```go
   type portalHandler func(http.ResponseWriter, *http.Request, portal.Identity)
   ```

   于是 `s.requireAdmin(s.portalMe)` 和 `s.requireUser(s.listNodes)` **都是编译错误**。（实际写出来验证过，不是推断。）

3. **作用域化取数**——因为第 2 条只挡住「接错守卫」，挡不住「守卫接对了但取多了」。一个 `func (s *Server) portalNodes(w, r, id portal.Identity)` 完全可以编译通过，然后在里面调 `s.st.ListNodes()` 把全机队序列化出去。

   所以门户展示的一切机队信息都来自 `portal.View`，而 **`package portal` 拿到的是一个窄接口 `portal.Data`，够不到 `*store.Store`**——在那个包里查别人的数据是编译错误。

   > **这条的边界要说准，别把它说得比实际强。** `package api` 里的门户 handler 是 `*Server` 的方法，仍然持有 `s.st`——`portalLogin`、`portalChangePassword`、`portalClaim` 就在直接用它读写自己的账号行。在那里写 `s.st.ListNodes()` 是能编译过的。真正的编译期保证只有两条：接错守卫，以及 `View` 路径上的越权取数。剩下的是规矩：**凡是要展示机队信息，一律走 `View`**。

4. **上下文不共享**。门户身份**从不**进 request context。这条比前三条弱：`rank` 检查在 `require()` 中间件里，不在 handler 体内，所以它并不能拦住一个绕过了中间件的调用——它保证的是不会出现「两个文件各自声明 `ctxKey` 常量、同一个 key 下的值被读成管理员身份」这类事故，以及审计不会把动作记到一个它其实不认识的身份上。

**长期规则（已写进 CLAUDE.md §4.13）**：`portal.Identity` 永不带 Role，`auth.rank()` 永不新增 `>= 1` 的值。一旦有人加了「user: 1」，`requireAdmin`（= viewer 档）覆盖的节点列表、用户列表、变量、Profile、流量与审计日志就全部对客户开放。

`GET /api/nodes/{id}/config/preview` **不在这一列**——M5-2 已经把它从 viewer 提到 `requireWrite`，正因为它返回的是完整装配后的 config.json，含每个节点的 REALITY 私钥与每个用户的凭证明文。读它比应用它更暴露，所以它不能待在其他 GET 所在的档位上。

`core/internal/api/portal_test.go` 有一个表驱动测试：一个有效的门户 token 对每一条管理路由拿 401，一个有效的管理 token 对每一条门户路由拿 401。

## 3. 曝光策略：白名单，不是减法

端用户看到的一切走**手写的投影类型**（`core/internal/portal/nodes.go`），不是在管理端 `nodeView` 上删字段。理由是失败方向不对称：**黑名单漏了就是静默泄露**（有人给 `nodeView` 加个字段，门户立刻开始下发，全程无报错），**白名单漏了只是界面缺个格子**。

这是 `template.Context.ForClient()`「把私钥分量整个从客户端渲染上下文里删掉」那条家规上移一层——同一套「可公开子集」的思路，对象从变量换成了节点字段。

不给端用户的字段，以及为什么：

| 字段 | 为什么不给 |
|---|---|
| `nodes.name`（内部名） | 常编码供应商与机房（`bwh-lax-3`），等于告诉对手去哪家发滥用投诉 |
| `public_ip` / `hostname` | 用户的客户端已经从订阅里拿到了地址，门户再给一遍对他零增益，却让「一个账号 + 一次 GET = 机器可读的全机队 IP 清单」成立 |
| `agent_version` / `xray_version` | 暴露跑的是哪个 Xray 构建，因而适用哪些检测特征；版本变化的时间点还泄露升级节奏 |
| CPU / 内存 / 磁盘 / 节点吞吐 | 容量数据，用户完全不可操作；节点级吞吐还是关于**其他订阅者**的实时侧信道 |
| `config_version` | 内部计数器，唯一读者是重连对账；公开它等于广播「配置刚改过」 |
| `last_seen_at` | 精确时间戳把门户变成封锁效果的反馈回路——对手实施封锁后比对这个值就知道生效没有 |
| `credentials[].secret` | 绝不。展示 UUID 会在 DOM、截图、工单里各留一份明文，并摧毁强隔离的意义 |
| `credentials[].email` | Xray 统计键，形如 `name.userID@profileID.nodeID`，暴露内部 id 空间 |
| `enabled` / `active` | 运维概念。`active` 是「节点被告知的状态」，推送 pending 时会对一个正常上网的人显示「未激活」 |

给的：`display_name`（新列，为空**不回落** `name`，见 §5）、三态 `availability`、以及该用户**自己**在该节点上的 24 小时流量。

`portal_exposure_test.go` 把上述每个禁用字段都填上可识别的值，然后直接 grep 响应字节。

## 4. Mai 的四条决策

| 决策 | 选择 | 影响 |
|---|---|---|
| 注册开放度 | **开放注册 + 共享注册码**（`CHIRAL_PORTAL_INVITE_CODE`） | 把限流从「顺手修的旧问题」变成**前置依赖** |
| 订阅 token | **改为可恢复存储** | 推翻 0003 迁移的注释；配套「无密钥则拒绝启动」 |
| 超限动作 | **只记录，不告警** | 整套告警状态机不做；`device_limit` 降级为展示阈值 |
| IP 粒度 | **存完整 IP，仅 superadmin 可见** | 主键改用 `ip_hash`，密文单独一列 |

### 4.1 注册

新注册的人**什么都拿不到**：建一行 `users`，不绑任何 Profile。这不需要任何新的准入代码——`Render` 遍历零个 profile 返回空订阅，`EnsureCredentials` 一个凭证都不铸，账号在构造上就是惰性的。门户显示「尚未开通」。

**注册响应对「邮箱已存在」保持完全一致**。最自然的实现是撞唯一索引后返回 409，那就是一个公开的客户邮箱枚举 oracle——而面板在管理员登录那条上正小心翼翼地避免同一件事。已注册的人从邮件得知，不从状态码得知。

`users.name` 是随机生成的，**绝不从邮箱派生**。两条理由：它是 `NOT NULL UNIQUE`，`mai@example.com` 和 `mai@example.org` 会撞；而且它经 `user.StatsEmail` 进入 `credentials.email`，被模板作为 `{{user.email}}` 渲染进订阅者自己的配置文件。

### 4.2 订阅 token 可恢复

`users.sub_token_enc`，AES-GCM 密封，AAD = `sub-token:<users.id>`。`sub_token_hash` 与 `/sub/{token}` 的查找路径一个字节不变。

代价说清楚：从「我们想拿也拿不回」降级为「持有 `CHIRAL_SECRET_KEY` 就能拿回」。鉴于面板本来就以同样形式持有每个用户的每一条代理凭证，边际损失很小。备选方案是「只能重新生成」，但那会在用户每次想看一眼链接时炸掉他所有已配置的客户端——那不是产品行为，是惩罚。

**配套硬约束**：门户开启且 `CHIRAL_SECRET_KEY` 为空时，Core **拒绝启动**，不是告警。订阅 token 是一条公网可用的 bearer URL，一份被拖走的 `chiral.db` 会直接产出全部用户的可用链接。

### 4.3 认领链接

管理员在用户页点一下生成一次性链接（`POST /api/users/{id}/portal-link`），形状和 `resetJoinToken` 一模一样。它同时是**没有 SMTP 时的找回密码路径**，所以不需要第二套流程。

因为它能接管账号，三条硬规则：

1. **token 走请求体，不走 URL path**。`/sub/{token}` 已经犯了把凭证写进反代访问日志、浏览器历史和 Referer 的错，对一个更强的凭证重复一遍是倒退。
2. **一次性**。
3. **账号已存在时只能改密码，不能改邮箱**。否则一条转发出去的链接可以把账号指向攻击者的邮箱，然后通过找回永久占有。

## 5. 节点对客名称

新增 `nodes.display_name`，为空**不回落**到 `nodes.name`。

回落听起来无害，实际是：迁移之后所有存量节点的 `display_name` 都是空，而 `POST /api/nodes` 只接受 `{"name"}`，新建节点也永远是空——所以门户上线第一天 100% 的节点都会走回落分支，把 `bwh-lax-3` 这类编码了供应商和机房的内部命名发给每一个注册用户。失败方向必须是「缺标签」，不能是「泄露标签」。

为空时服务端返回 `index`（该用户列表内的 1-based 序号），由前端渲染成「线路 01」/「Line 01」。服务端不发明面向用户的字符串——它不知道该用哪种语言发明。

## 6. 可用性从哪来

直接读 `node_alert_state.announced_online`，不发明第四套判定。那张表由 `alert.Service.Sweep` 在现有 60 秒 ticker 上推进、带 2 分钟去抖，并且即使一个告警目标都没配也照样维护。

于是「去抖」这个需求塌缩成一行数据源选择，零新增机制，而且门户显示的红绿与 Telegram 告警的时间天然对得上（不然排障时会有两个真相）。诚实的耦合：门户状态的更新延迟 = sweep 周期 + 去抖 ≈ 最多 3 分钟。

**绝不把 `users.active` 折进可用性**。它是每用户一个布尔，不是每（用户 × 节点）；一次 SyncUser 部分失败会让某个用户的**整个**线路列表同时变红，而他正连着上网。

## 7. 在线地址记录

默认关闭（`CHIRAL_ONLINE_RECORD`）。开启后 Core 给每个 Agent 下发 `OnlinePolicy`，Agent 每 30 秒用 `xray api statsgetallonlineusers` + `statsonlineiplist` 取一次快照回报。

### 7.1 `OnlineReport` 是绝对快照

这是对 CLAUDE.md §7 增量规则的**明确豁免**。两者的失败模式相反：流量计数器因 Xray 重启归零，所以绝对值会歪曲总量；而观测集合归零的含义是「**没在观测**」，绝不能读成「零设备，解除限制」。所以即使没人在线也每轮发一个空的 `complete=true` 帧——让沉默保持有歧义这件事不发生。

### 7.2 来源校验

每条上报都要对着它声称的凭证核验，**节点只能为发给自己的凭证说话**。Agent 跑在租来的机器上，没这个检查，一台被攻陷的 VPS 就能给任意订阅者编造两百个地址——而那些地址会落进 `user_devices`，也就是运维日后当作「共享证据」来读的那张表。伪造的证据栽在一个无辜用户头上，比没有这个功能糟得多。

### 7.3 落库形态

```sql
PRIMARY KEY (user_id, ip_hash)   -- SHA-256(ip)，稳定
ip_enc TEXT NOT NULL             -- AES-GCM 密封的完整地址
```

主键不能是密文：AES-GCM 是随机化的，同一个地址每次密封出不同字节，upsert 会变成每次观测插一行。哈希给稳定键，地址本身进 `ip_enc`。

`ON DELETE CASCADE`，**刻意不同于** `traffic_buckets` 的「无外键 + `''` 哨兵」。那条注释的理由是「删除用户不能抹掉机队自己的历史」——字节总量在主人走后仍有聚合意义；**一个 IP 不是机队总量，是那个已被删除的人的住址**。让它在哨兵下再躺 30 天、任何 UI 都够不着、因而永远没人复核，是最糟的形态。

保留 30 天（`store.DeviceRetention`），短于流量的 90 天：这是个人数据，而且一个月前的地址回答不了任何运维问题。两个窗口不一致是决策，不是疏忽。

## 8. 对着真实 Xray 26.3.27 实测的结论

以下都不是从文档推断的，是跑两个内核、过真实字节测出来的（复现见 `agent/internal/xray/online_live_test.go`）：

| 实测 | 结果 |
|---|---|
| `online` 计什么 | **不同源 IP 数，不是会话数**。同一 IP 的 3 条并发连接 → `value: 1` |
| `rmu` 能断已建立的会话吗 | **不能**。前后都是 6 条 ESTABLISHED，一条没断，只拒新连接 |
| `sib`（按源 IP 封锁） | 能用，但也**只挡新连接**；需要 `RoutingService`；且是 per(inbound, IP) 不是 per(user, IP)，封一个 NAT 出口会误伤同址其他人 |
| 无 `statsUserOnline` 时 | 流量照常统计，online 三命令**静默失效**——`statsgetallonlineusers` 返回 `{}` 且 **exit 0**，`xray -test` 一声不吭 |
| 回环源地址 | **被完全排除**在统计外。本地测试时看起来和功能坏掉一模一样 |
| 断开后残留 | 约 2 秒即消失，**无缓冲窗口**——轮询间隔就是采样误差的全部 |

**两条直接后果**：

1. **「超限自动断线」在 Xray 这一层不存在**。唯一真能断的是重启 Xray，而那会掐掉该节点上所有人的连接。这不是我们选择不做，是内核没有这个能力——所以表里没有 `suspended_until` 之类等着一个建不出来的机制。

2. **打开这个功能必须给每个节点注入 `statsUserOnline`**，也就是一次配置版本变更 + 一次 Xray 重启（该节点上的活连接断一次）。`RoutingService` 在同一次改动里一并加上——它是将来做 `sib` 需要的，晚加就是第二次全机队重启换一行 JSON。

### 8.1 这个功能的硬上限

**IP 不是设备。** 一台手机 wifi 转蜂窝是两个地址；IPv6 隐私扩展让它一天漂成好几个；一户人家 NAT 后是一个地址。**低于 3 的上限一定会误报**。所以管理端和门户的文案全程是「并发地址」，一次都没说「设备」。

**共享账号上，「你的地址」会把其他共用者的地址展示给任何一个登录者。** 那是用户对用户的 IP 披露，而被披露的人常常不是账号主人。这是「让用户自查账号有没有被别人用」在一个**按定义有时被共享**的账号上不可避免的形状。

## 9. 已知的取舍与没做的东西

- **门户首页不自动刷新**。管理台每 10 秒轮询是因为有人在盯机队；门户是客户查配额，而 N 个客户轮询一个由 `MaxOpenConns(1)` 的 SQLite 支撑的页面，是廉价的写锁竞争源。手动下拉刷新。
- **端用户没有 MFA**。它守的东西比 `/sub/{token}` 已经免费给出去的还少——那是一个没有 MFA、没有过期、没有限流的 bearer token。`portal_challenges` 的 CHECK 已经预留了 purpose，将来加不用重建表。
- **没有自助找回密码**。走管理员发的认领链接，这样有没有 SMTP 都能用。
- **没有邀请码/套餐码系统**。一张 13 列的表 + 三条路由 + 新 UI 面，为的是一个没提的需求；一个环境变量的共享注册码够用。
- **可用性绿点仍是一个弱 oracle**：对手怀疑某 IP 属于机队时，可以比对该 IP 的可达性与面板状态的相关性。这是对外售卖状态的固有代价，接受并记录。
- **门户前端的隔离是纪律不是结构**：`src/portal/` 不 import `src/api.ts` 和 `src/pages/` 时才成立。实测门户 chunk 209 kB 且 Monaco 不可达，但一次疏忽的 import 就能破掉。要让它变成结构，得付一个断言构建产物模块图的构建守卫的成本。
