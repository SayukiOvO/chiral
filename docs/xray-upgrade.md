# Xray-core 运行时升级（M6）

面板要能把节点上的 Xray-core 换成新版本，而且要追 **prerelease**：xhttp 上下行分离、后量子 REALITY 这些特性只在快照版有，稳定版发布很稀疏（CLAUDE.md 决策 9）。追快照的代价是「新版本更可能起不来」，所以整条链路是围绕**这件事一定会发生**设计的，而不是围绕它不该发生。

## 1. 一句话流程

```
管理员选版本 + 选一台金丝雀
  → Core 先给自己装一份（校验用）
  → Core 通知那台节点安装
  → Agent 取货 → 校验 SHA-256 → 解包到 kernels/<版本>/ → 重启进去 → 拿客户端真的上一次网
      ├─ 字节回来了                → ACTIVE
      ├─ 没东西可测 / 基线本来就不通 → INCONCLUSIVE
      └─ 起不来 / 本来通现在不通    → 自动回滚旧二进制 → ROLLED_BACK + 立即告警
  → 管理员看结果，手动「放行到全部节点」
  → 阻塞了就修，修完一键「再试一次」（仍然从金丝雀开始）
```

## 2. 三条硬边界

### (a) Core 先给自己装，才通知别人装

`xray -test` 只对**跑它的那个 build** 有效。节点升到 26.7.11 之后，用 26.3.27 去校验它的 config，新特性全被当成未知字段拒绝——升级白升；反过来，用新的去校验没升的节点，面板会痛快放行一个根本起不来的 config，那是**节点直接躺下**，直到有人发现。

所以 `upgrade.InstallOn` 里，`s.fetch.Install(...)` 一定在 `SendXrayInstall` 之前，失败就整个拒绝。这保证了「面板能校验的版本集合」⊇「机队在跑的版本集合」，也就是 `core/internal/kernel` 存在的全部意义。

注意两份归档不是一份：
- **校验用**：Core 自己平台的 build（`kernel.Platform()`）。
- **中继用**：节点平台的 build，跟 GitHub 会发给它的字节一模一样。

拿面板自己那份去喂一台 arm64 节点，SHA-256 对不上（对上了才更糟——那说明校验形同虚设），最后在 exec 时失败，什么线索都没有。

### (b) 按节点的内核校验配置，但**不因此拒绝下发**

`profile.Service.kernelFor(nodeID)` 读的是 **`xray_installed_version`**，不是 `xray_version`。理由：现在推一个 config 过去，节点是**重启进磁盘上那个 build** 去应用的；升级窗口里用 running 的版本校验，恰好是反的。

面板没有那个版本时，退回到自带的二进制，`Exact=false`，**如实告诉操作员**（预览徽章变灰、写明用哪个版本校验的），但不拒绝。真正的闸门是 agent 本地那次 `xray -test`——它跑的才是对的二进制。在这里拒绝，等于把每一台面板还没跟上的节点都锁死，而升级过程中每台节点都是这种状态。

### (c) 结果是三值的，而 ACTIVE 的判据是「客户能上网」

`ACTIVE` / `INCONCLUSIVE` / `ROLLED_BACK`，不是「成功/失败」。

**判据换过一次，这一段是全文最重要的地方。** 原来的探活是 `xray api statsquery`：内核把 config 解析了、端口也听上了，它就应答。问题是**一个传输层已经坏掉、订阅者全黑的节点，这个探活照样通过**——而那恰恰就是升级会造成的故障形状（REALITY 参数变了、xhttp 语义变了、flow 变了）。旧判据会给它盖 ACTIVE，然后请管理员把这个版本推给整个机队。

这不是推理，是实测出来的：`agent/internal/xray/dataprobe_test.go` 里的 `TestTheAPIAnswersOnANodeThatCarriesNoTraffic` 起一个真内核，API 一切正常，同一时刻没有任何客户端能通过它送出一个字节。

所以现在 agent 会**真的当一次客户**：

1. Core 在下发 config 的同时，用**订阅那套 xray-json 客户端模板**、拿一个**真实订阅者的凭证**渲染出一个 outbound，塞进 `ConfigPush.probe_outbound_json`。
2. Agent 用**被测的那个二进制**另起一个一次性内核，配置 = 本机 SOCKS inbound + 那个 outbound。
3. 通过这个 SOCKS 去取 `probe_url`（默认 `http://cp.cloudflare.com/generate_204`，`CHIRAL_PROBE_URL` 可改）。
4. 字节回来了才是 ACTIVE。

链路是：探测客户端 → 本机 SOCKS → **本节点自己的 inbound** → 本节点的 outbound → 外网。也就是客户走的那条路，一段不少。

**为什么客户端配置由 Core 渲染，而不是 agent 从 server config 反推**：反推意味着 agent 要自己算 REALITY 公钥、镜像每一种传输设置，并且以后每加一个协议都得跟一遍——这就是 CLAUDE.md §7 里说的「两份实现必然会漂移」。面板本来就有且只有一处知道怎么写客户端侧，就是那份手写的 xray-json 模板。**探测拨的就是客户拨的**，这个性质是白拿的。

**为什么用真实订阅者的凭证，而不是造一个探测账号**：造账号意味着机队每台机器上永久多一份凭证，就为了一个只在升级时跑的检查。复用已经在那儿的凭证**一点额外暴露都没有**——agent 本来就是自己把那份凭证写进 config.json 的。代价是升级期间给某个用户记上几百字节。

三个值的含义因此变成：

- `ACTIVE` = 有客户端通过这个节点上了网。
- `INCONCLUSIVE` = 起来了，但**没东西可测**：节点没绑 profile、profile 没有 xray-json 模板、没有启用的用户，或者升级前的基线本来就不通。**每一种都会连原因一起报上来**——只说「无法确认」会让人白找半天，而这几种的修法都是一行。把它折进 ACTIVE，金丝雀就成了橡皮图章。
- `ROLLED_BACK` ≠ `FAILED`。前者说「旧内核已经在服务了」——凌晨三点被叫醒的人最需要知道的就是这一句：是在看一次故障，还是在看一个决定。

**基线**：切换前先用**当前正在服务的那个二进制**跑一次同样的探测。判据是「本来通、现在不通」，不是「现在不通」。敢用「真的取一次 URL」这么重的判据，靠的就是这一条——所有不是新内核的锅的失败原因（节点没用户、机房 egress 被挡、上游挂了），在动内核之前就已经先失败一次了。

## 3. 两条取货路径

| | 直连 GitHub | 经 Core 中继 |
|---|---|---|
| 谁发起 | Agent | Agent（**拉**，一次一块） |
| 何时用 | 默认，先试 | 直连失败且 `relay_available` |
| 代价 | 节点要有出网 | 每块一个 RTT |

中继是**拉模式**，这一点是有意的：节点的发送队列只有 16 帧，而且 config push、用户增删都共用它。推一个 21 MB 的归档过去，要么被丢，要么把那些挤掉。让 agent 主动要下一块，等于把在途帧数钉死在 1——不需要调任何限速参数，也饿不着任何东西。

中继**不是可信路径**：同样的字节换根管子而已，而面板恰恰是攻击者最想站上去的那台机器。所以 SHA-256 校验对两条路一视同仁，没有校验和就直接拒装。Core 也只肯中继**它自己刚刚让这个节点装的那个版本**，否则面板就成了一个任人差遣的下载代理。

## 4. 容器重启不能偷偷降级

Agent 把当前激活的版本写在 `<state>/kernels/active`。重启时：

- 有记录、版本确实装着、而且那个二进制**自己报出来的版本对得上** → 用它。
- 否则 → 用镜像里烘焙的那个（地板）。

三个条件缺一不可。指向一个不存在的路径，agent 起不来；指向一个标错的 build，就会悄悄跑一个没人点名过的版本——那正是按版本校验想防的事。

同理，每个版本目录里都带着**自己那份** `geoip.dat` / `geosite.dat`，启动时 `XRAY_LOCATION_ASSET` 指向它，而不是镜像里旧版本的那份。

## 5. 状态机（机队级）

```
                  ┌──────────┐
   开始金丝雀 ───▶ │  canary  │
                  └────┬─────┘
           ACTIVE /    │    ROLLED_BACK / FAILED
        INCONCLUSIVE   │              │
                  ┌────▼──────────┐   │
                  │awaiting_promote│  │
                  └────┬───────────┘  │
             人工放行   │              ▼
                  ┌────▼─────┐   ┌─────────┐
                  │promoting │──▶│ blocked │
                  └────┬─────┘   └────┬────┘
                  全部就绪 │           │ 修完「再试一次」
                  ┌──────▼──┐         │ （回到 canary，不跳过）
                  │  done   │◀────────┘（或「结束这次升级」）
                  └─────────┘
```

**`awaiting_promote` 不是实现细节。** 自动往下走的升级，会以机器的速度把一个坏版本变成全机队故障；金丝雀的全部价值就在于有个人看一眼结果。

**同一时刻只能有一个升级在飞**，由数据库的唯一索引保证（迁移 0012 的 `active_marker` 生成列），不是 Go 里的一次检查——检查有读写窗口，而这恰好是两个管理员会同时按的按钮。

`blocked` 之所以独立于「done 但有失败」，是因为它是**管理员修完东西之后重试的起点**，也就是需求里的最后一条。重试仍然从金丝雀开始：修复在被一台节点证明之前，只是一个假设。

## 6. 告警绕过 debounce

节点在线告警有 2 分钟的稳定期（`alert.Debounce`），因为掉线会抖。内核回滚**不抖**：它只发生一次，是某人刚刚做的事的直接后果，而且被通知的时候早就结束了。等两分钟才说，等于把这条通知唯一的价值——在按下按钮的人还盯着屏幕时到达——给延迟掉。所以走 `alert.Announce`，立即发。

回滚的告警里会明写「节点已经用 <旧版本> 恢复服务」，并且 `Online: true`：这不是一次掉线事件，靠 `Online` 字段做判断的 webhook 不能读错。

## 7. 部署要点

| 变量 | 位置 | 为什么 |
|---|---|---|
| `CHIRAL_KERNEL_DIR` | Panel，**必须在数据卷上** | 每个版本一个二进制。放容器本地路径，重启就忘光，面板会拿镜像里那个去校验一个已经升级的机队 |
| `CHIRAL_GITHUB_TOKEN` | Panel，可选 | 匿名 GitHub API 每 IP 每小时 60 次。单面板永远碰不到，共享出口 IP 可能会——然后升级就悄悄不再被提供 |
| `CHIRAL_STATE_DIR` | Agent，**必须在数据卷上** | 装好的版本 + `active` 指针都在这里 |

Panel 镜像照旧烘焙一个 Xray（地板 + `xray -test` + ML-DSA-65 派生），Agent 镜像也照旧烘焙一个（地板）。烘焙的那份**永远不会被删**，它是所有「什么都没有时用什么」的答案。

## 8. 已知边界

- **回滚只往回，不往前。** Agent 不会自己再试新版本。一台刚刚启不动新内核的机器，是整个系统里最没资格决定下一步试什么的东西；而两台节点各自独立做这个决定，机队就会进入没人设计过的状态。往前走是 Core 的事，且要人点。
- **promoting 阶段的失败会把整个升级打到 blocked**，即使只有一台节点没通。此时机队跨着两个内核版本——这正是需要人来决定怎么办的状态，不是可以静默记账的状态。
- **探活只探 `xray api statsquery`。** 它证明内核起来了、gRPC API 在服务，但**不证明代理链路通**。真正端到端的探测需要在节点上起一个客户端连自己，成本和复杂度都高一档，目前没做——所以 `ACTIVE` 的准确读法是「内核活着且在应答」，不是「用户能上网」。
