# 外部节点

别人提供的节点：机场订阅，或朋友直接发来的一条链接。这些机器不是你的，装不了 Agent，所以面板对它们做不了它对自有节点做的任何事。

**先说清楚能力边界**，这是「对方给你一条链接」这件事本身的性质，不是以后能补的缺口：

- **所有订阅者共用同一份凭证**——对方只给了你一条，没有按用户隔离。
- **没有流量统计**——流量在对方那边计，面板看不到。
- **停用某个用户不会让他连不上**——凭证不是面板发的，收不回来。
- 只出现在 Clash 类订阅里（`clash` / `stash`）。xray-json 与分享链接不含它们。

## 来源

两种：

- **订阅链接**——每天自动更新一次。
- **直接粘贴**——不自动更新，适合朋友发来的单条链接。

格式**自动识别**，因为机场不会告诉你它给的是哪种，同一家换个套餐都可能变：

| | |
|---|---|
| Clash YAML | 取 `proxies:` 段 |
| 分享链接列表 | 每行一条 |
| 整体 base64 的链接列表 | v2rayN 风格订阅的常见形态 |

链接支持 `vless://`、`vmess://`、`trojan://`、`ss://`，含 REALITY 与各种传输参数。

**解析不了的单条会被跳过，不牵连整个来源**——机场经常带上面板没见过的协议类型，其余的照样能用。跳过的会连同原因记在来源的错误里；只跳不说，会让「十个节点解析出七个」和「这个来源就七个节点」长得一模一样。

**传输参数认不出来时是报错，不是忽略。** 这条是踩出来的：早期只认 `ws` 和 `grpc`，别的默默跳过——而跳过传输不会产出一个「没有传输的节点」，它产出的是一个**自称裸 TCP 的节点**。一条 vless+REALITY over xhttp 就这样变成了格式完全正确的 TCP 代理：面板列得出来、mihomo 加载得了、`xray -test` 无话可说，而订阅者拿到的是超时，控制台还一口咬定这个节点没问题。少一个节点会被去查，多一个坏节点不会。

目前认识的传输：`tcp`/`raw`（含 `headerType=http`）、`ws`、`httpupgrade`、`grpc`、`http`/`h2`、`xhttp`/`splithttp`。

**粘贴进来的来源也能「重新解析」。** 没有 URL 不代表没东西可重读：解析器会长本事，而一个用旧版本导入的节点，如果没有重新解析的入口，就会永远保留旧版本对它的理解。上面那个 xhttp 的故障之所以能一直躺在订阅里，正是因为修好解析器之后没有任何办法让它再读一遍。

## 前置：中继（经自有节点）与链式（经外部节点）

「经由」有两种，取决于前置是谁：

**经由自有节点 = 服务端中继。** 对方机场变成我们节点上的一条 outbound，订阅者连的是**我们的** inbound、用**我们签发的**凭证，一条 routing 规则按凭证的 email 把他的流量送出去。订阅里那条代理名字是对方的、**地址是我们的**，落地地址订阅者永远看不到。

这不是锦上添花，它把外部节点原本做不到的三件事一次补齐：**按用户隔离**（每人每出口一份独立凭证）、**流量统计**（凭证就是统计键）、**停用即断**（凭证在我们手上）。顺带还解决了客户端兼容——订阅者的客户端只需要会我们的协议，对方是不是 xhttp 无所谓（Stash 根本不支持 xhttp）。

代价是流量绕一圈，走我们节点的带宽。

**经由外部节点 = 客户端链式。** 对方的机器我们控制不了，只能让订阅者的客户端自己串（clash 的 `dialer-proxy`）。所以上面那三件事在这条路上依然做不到。

被中继的外部节点**默认不再作为独立代理下发**——把落地地址一并交出去，等于把中继的意义抵消掉。想要一条直发的线可以单独打开（控制台上那个「中继·已隐藏 / 中继·并直发」）。

一个推论：**外部节点 B 不能再「经由一个已被中继的外部节点 A」**。A 已经没有客户端侧的存在，B 的 `dialer-proxy` 无处可指，B 会被整条略去。要串就把 B 也设成经由自有节点。

### 凭证与路由

凭证粒度从「用户 × 接入配置 × 节点」扩到「**× 出口**」，因为路由规则只能靠 email 区分同一个 inbound 上的不同出口。出口的规则**排在运维自己的规则之前**：routing 是首个匹配优先，而「全部走 direct」是所有骨架的常见形状，它会把中继流量吞掉、从本机出去——**连接是成功的**，看起来和正常工作一模一样，只是出口错了。

没有任何人有权使用的出口，只给 outbound、不给规则：空的 `user` 列表匹配的是**所有**用户，而不是没有用户。

## 链式代理（经外部节点）

每个外部节点可以单独指定前置，**可以是本机队的节点，也可以是另一个外部节点**。这样对方看到的是前置那一跳，而不是订阅者。

前置能选外部节点这件事不是锦上添花：一条中继买自 A 家、出口买自 B 家，中间根本没有自己的节点可指。早期 `chain_node_id` 的外键指着 `nodes` 表，于是这个最典型的组合恰好是唯一表达不了的。现在两列并存（`chain_node_id` / `chain_proxy_id`），一次只设一个。

链可以多跳：`C → B → 自有节点`，Clash 会逐层套下去。

**环路在写入时就被拒绝**（自环，以及 A→B→A 这类绕回来的）。放到渲染时再处理也行，但那样的后果是两个节点从所有人的订阅里一起消失，而运维在面板上看不出任何异常——报错的时机必须是他按下那一刻。

Clash 侧落成 `dialer-proxy`。有一处不显然：**`dialer-proxy` 必须指向同一份文档里存在的代理**，否则客户端拒绝整份配置。所以当某个订阅者拿不到前置时，该外部节点会被**整个略去**，而不是降级成直连——降级会把这个设置存在的意义悄悄取消掉，而订阅者不会知道。

**用自有节点做前置，节点的 `sniffing` 必须加 `routeOnly`。** 这条踩过：`destOverride` 会把连接的目的地址改写成嗅探到的域名——对订阅者自己上网这正是要的，能让域名规则匹配上；但对一条**替别人中转**的连接是致命的，因为那条连接本身是一次 TLS 握手，携带的是对方机场的伪装 SNI，于是目的地址被从「客户端要求的落地 IP」改写成那个域名解析出来的地址，拨不通，而报错里不会提到 sniffing。加 `"routeOnly": true` 后嗅探结果只用于路由匹配、不回写地址。面板会对没加的 inbound 给出提示。

这个「略去」是**传递**的：`C → B → 自有节点`，订阅者要是拿不到那台自有节点，B 和 C 一起消失。所以渲染不能只扫一遍列表——A 可能在决定它依赖的 B 之前就被访问到——而是迭代到不动点。控制台上每个受影响的节点会标出它**直接**失去的那一环，顺着看就能找到断点。

## 改名

节点在订阅里叫什么，由你说了算。机场往名字里塞的东西经常不是名字——剩余流量、到期日、账号的一段 slug——而那串字符会原样进到每个订阅者的客户端里。

**对方给的名字不会被覆盖，只是被盖住。** 它是刷新时用来认领这一行的依据（见下一节），改掉它，下次刷新就会把这个节点当成没见过的新节点插入，链式设置和按用户的禁用全部跟着丢。所以库里存两个名字：对方的照旧，你起的那个存在旁边，有就用它。

改名之后 `dialer-proxy` 会跟着改。这不是顺手：dialer-proxy 引用的名字必须在同一份文档里定义得出来，而文档里定义的是你起的名字——两边不一致，客户端拒绝整份配置。

## 刷新与设置保留

刷新会重新解析并替换节点列表，但**每个节点上的设置（链式、启用）会带过来**：先按名字匹配，名字变了再按 `server:port` 兜底。

机场经常把剩余流量和到期日写进节点名（`🇭🇰 香港 01 | 剩余 82%`），只按名字匹配的话，对方每改一次标签你的链式配置就断一次——而且没人会想到去复查。

## 顺序

外部节点和自有节点排在**同一个列表**里（控制台「节点」页底部的「订阅顺序」）。分开排表达不了「这个外部出口紧挨着它链经的那台自有节点」这种安排。

这个顺序还决定**每个策略组内的顺序**：组的成员是生成器遍历渲染好的 proxies 列表、按各组的正则挑出来的，挑到的先后就是列表里的先后。所以「节点选择里的顺序」不是第二个设置——只有一个设置，也就不存在两个设置互相打架。顺带地，`select` 组打开时选中的是第一个成员，所以排在最前的那个就是客户端的默认节点。

没排过的（新加的节点、新来源里的新节点）排在所有排过的后面，各自保持原有的稳定顺序。这样新增一台机器是出现在列表末尾，而不是插进中间。

## 与规则的关系

外部节点像自有节点一样出现在 `proxies` 里，因此会被分流规则的策略组正常选中。规则本身不区分节点来源。

## 边界

- **新加进来的外部节点默认谁都不能用**，要逐人放开。机场往列表里加一台机器，不等于运维决定把它发出去——不这样的话，对方加一个节点，下一次刷新它就静默出现在每个订阅者的客户端里，没有任何一步问过。刷新时只有真正新增的行会写拒绝，已经放开过的不受影响。（在此之后创建的订阅者不在此列：新人能用什么由授予他的接入配置决定，而不是由一堆他没听说过的节点决定。）它不像自有节点那样挂在接入配置下——外部来源没有 profile 可绑，所以这就是它唯一的开关。
  同一份数据两个入口，看你手头在做哪件事：本页每个节点的「谁能用」是**从节点看人**（刚加完一个来源时想的是这台机器给谁），用户页的「可用节点」是**从人看节点**（见 `user-management.md` §按用户指派节点）。两边写的是同一批行，改哪边另一边立刻可见。
- 面板不校验对方节点是否可用——没有 Agent，无从探测。节点显示为可选，通不通要客户端自己测。
- 来源可整体停用，单个节点也可单独停用。
