# 3x-ui 集成设计

## 目标状态与当前边界

完成当前接管口径全部验收后的**目标状态**是：Chiral 不再自行承担 Xray-core 的进程、版本与
运行时 API 适配，而把这些职责交给每台节点上的 3x-ui。**Panel、Core 与 Agent 仍然保留**：
Agent 继续主动连接 Core，并在本机调用 3x-ui API。这样不要求节点开放管理端口，也不改变
现有的 NAT / CGNAT 连接模型。

当前第一阶段尚未切换执行权：`direct-xray` 仍是唯一接收写入并服务订阅者的 ACTIVE provider，
`3x-ui-shadow` 只在旁路读取状态和契约。两者可以同时运行，但一次只能有一个 ACTIVE owner；
本阶段 Agent 不向 3x-ui 发送任何配置、用户、流量或生命周期写操作。

SHADOW 现在只调用状态、OpenAPI 和已持久化的出站统计读取，不再自动读取最终配置。
官方 `getConfigJson` 组装配置时可能运行到期、额度与续期维护，模板读取也可能修复旧存储；
二者虽是“读取”，仍不能进入旁路观测。最终配置回读保留给明确授权的候选写入和接管验收。
认证本身仍可能更新 token 使用时间，因此“只读”不是整个上游数据库逐字节不变的保证。
本阶段真实验证仍限定为 Chiral 自有的空隔离实例，不能自动指向未授权的既有实例。

`SHADOW` 的只读边界不等于部署过程零中断。为现有 Agent 添加环境变量或 token 挂载会重建
容器；Agent 退出时会停止其管理的 Xray 子进程，已有连接随之中断。要求保留现有连接和数据时，
应使用 [`deploy/3x-ui-lab`](../deploy/3x-ui-lab/README.md) 的独立实验项目，不修改生产 Agent。
实验项目包含官方 3x-ui、全新 Core 和 Agent，采用无外部网络的共享回环命名空间与专属数据卷，
不接入生产控制面，不读取生产凭证。实验验证仅能证明实际覆盖的契约与上报行为，不能代替下述
生产接管门槛。

3x-ui 是节点侧的执行后端，不是第二个控制面。日常管理仍在 Chiral 完成；不把用户跳转到
3x-ui，也不把 3x-ui 页面嵌入 Chiral。破窗排障只能通过 SSH 端口转发访问只监听本机的
3x-ui，手工修改产生的漂移必须显式采纳或由下一轮调和覆盖。

迁移期保留 Agent 的原生 Xray 后端，新增 `3x-ui` 候选 provider。两种 provider 共用 Core ↔
Agent 协议所表达的配置版本、事件和确认边界；流量与在线能力按下述已确认口径呈现。3x-ui
只能提供近期用户／IP 时，不得把近似记录塞进完整 `OnlineReport` 或伪造 `complete=true`。
原生 provider 是节点级回滚路径，不在首个集成版本中删除。

## 上游约束

3x-ui 采用 [GPL-3.0](https://github.com/MHSanaei/3x-ui/blob/main/LICENSE)。Chiral 只通过
HTTP API 调用未修改的独立进程或容器，不复制、链接或复刻 3x-ui 内部实现。
2026-09-29，用户已撤回独立增强分支授权：不得修改 3x-ui、维护增强 fork，或通过新增兼容
服务绕过此限制。3x-ui provider 也不得直接读取 Xray API 或管理本地内核缓存。官方 API 尚
无法满足的接管要求必须如实保留为未完成项；只有用户能调整产品口径，不得由实现者自行
降低标准或重新请求同一增强方案。

同日用户明确调整升级范围：节点内核的预安装不激活、离线旧内核回滚暂缓，不再阻塞当前
迁移验收；当时其余门槛不变。此决定不授权生产升级，也不改变禁止修改上游的边界。普通在线
自动更新可使用原版版本查询、指定版本安装和运行状态接口，由 Chiral 负责调度。当前已实现
窄类型 HTTP 调用、持久化候选编排、受限出网隔离运行器和实验专用可选 DNS-over-TLS，尚未
接入 Core 自动调度或 ACTIVE provider。2026-09-30 的第 05 次官方原版 HTTP 实验明确通过
`prepare` 与 `baseline-rebuilt`：从内置 26.9.9 的镜像真实安装 v26.9.8，一次派发、零重放，
HTTP 数据探针、配置和凭证保持及新容器的卷内版本持久性均有正向证据。随后 v26.9.9 更新
结果未知且服务不可达；第 06 次 prepare 也以未知结果和服务不可达结束。两次均未重试未知
操作，没有完成 target rebuild 或四阶段整体验收。安装会停止并重启 Xray，不能保证现有连接不中断。

2026-09-30，用户另行确认五项接管口径：在线信息接受官方 HTTP 提供的近期用户／IP 近似值，
但不得冒充完整快照；计费接受原版采集对象初始化时首批非空计数只建立基线所造成的不可恢复
缺口，且缺口上限未知、不能假定每次可检测。这两项已知差异不再单独阻塞接管。配置仍须保留
全部字段，日常用户操作不得为弥补字段缺失而额外中断连接；失败配置不得影响旧运行态。普通
更新采用保守自动恢复，结果无法确认时停止自动写入并转人工。该决定不启用 ACTIVE、不授权
操作 Turin，也不授权修改上游。

上游 [README](https://github.com/MHSanaei/3x-ui#disclaimer) 明示项目面向个人使用且不建议
生产部署，[安全策略](https://github.com/MHSanaei/3x-ui/security/policy) 只为最新版本提供安全
更新。采用它可以降低 Chiral 对 Xray 适配的维护量，但不能把上游声明转化成生产保证。因此
Chiral 必须保留契约测试、金丝雀、可逆 provider 和自己的真实数据路径判据，并在安全更新与
兼容性之间逐次做受控升级。

## 职责与数据主权

| 数据或能力 | 权威来源 | 3x-ui 中的角色 |
|---|---|---|
| 管理员、订阅者登录与 RBAC | Chiral Core | 不同步 |
| 用户、组、节点授权与受限目的地 | Chiral Core | 只接收已裁决的运行时结果 |
| Profile、变量、凭证与中转线路 | Chiral Core | 作为受 Chiral 管理的 inbound、client、outbound/routing 投影 |
| 订阅 token 与客户端模板 | Chiral Core | 禁用 3x-ui 订阅服务，不生成第二套订阅 |
| 配置版本、审计与回滚历史 | Chiral Core | 保存当前运行投影及迁移前快照 |
| Xray 安装、启动、停止与热应用 | 节点 3x-ui | 权威执行者 |
| 节点运行指标 | Chiral Agent | 3x-ui 仅提供 Xray 相关观测 |
| 用户流量与在线地址 | Chiral Core 汇总 | 3x-ui 提供原始累计计数器和近期用户／IP 近似记录 |

3x-ui v3 的 client 是可关联多个 inbound 的全局对象，而 Chiral 的安全边界是
`用户 × Profile × 节点`（必要时再含出口）各用一份独立凭证。因此不能把一个 Chiral 用户
映射成一个共享的 3x-ui client。每条 Chiral credential 映射成一个仅属于一个受管 inbound
的 3x-ui client，以现有唯一统计 email 作为外部键；Core 再把这些运行时记录聚合成人类
用户的用量和状态。

受管对象必须带稳定的 Chiral ownership 标识。3x-ui 的数字 ID 只作缓存，不作身份；数据库
恢复后应按 ownership 标识重新发现。Agent 只能更新或删除带有本节点 Chiral 标识的对象，
不得清理无法证明归属的配置。

候选 `OwnershipScope` 已实现纯内存的归属前置校验：HMAC 元数据绑定 3x-ui 实例 GUID、
随机 Chiral owner ID、对象类型和现有 Tag／Email，标识只放在 Remark／Comment，不改变
路由、计费外部键或用户凭证。校验完整清单与回读对象，拒绝重复、缺失、额外受管对象、
同名外部对象、无效标识以及双向跨归属绑定；每条受管凭证只能绑定清单明确指定的一个入站，
移到另一条受管入站也不能自动通过。数字 ID 可以在数据库恢复后重新发现。

该纯校验组件不调用 HTTP、不派发写入，也不授予访问权限。候选 `OwnershipStore` 另行保存
实例／端点绑定、随机标识密钥、完整清单及模板／配置摘要。只允许在新建的私有目录首次
初始化；重开时状态缺失、损坏或绑定变化均失败关闭，不自动重置身份。状态使用私有普通
文件、目录锁和同步后的原子替换；运行期间发现文件身份、权限或内容变化后拒绝继续。

每次候选写入须先持久化唯一 pending 意图；同一目录中的组件使用者被串行化。重启后 pending
仍阻止所有新写入，包括相同请求重放。只有调用方明确收到完整成功 HTTP 响应，且回读与
意图中的完整检查点一致，才可推进代次；“回读看起来已完成”不能替代丢失的响应。此组件
本身不发送 HTTP，也不提供强制清除、补偿或重试入口。完成记录最多保留 128 项，满后停止
接受新操作而非淘汰防重放记录；正式运行接线前仍须设计有外部代次锚定的长期收据策略。

上述锁不覆盖升级日志或其他 3x-ui 写入者，检查点不代表运行内核已采用配置，也不证明
数据面正常。完整写入协调、删除前最终计费确认和配置失败隔离仍待实现，不进入 ACTIVE。
HMAC 用于避免意外跨管理，不防控制两端进程或恢复整库的管理员；上游没有 CAS，成功的
快照检查也不能排除之后的外部并发修改，不能把返回的 ID 当作可长期使用的写入授权。
私有目录整体被替换或恢复到旧备份不属于本地锁／状态校验的防回退保证。

用户 attach／detach 已提供窄类型 HTTP 方法，拒绝空、非正数及重复入站 ID，保留 Email
路径转义和敏感错误脱敏；模板读取及这两项操作作为候选可选能力发现，不扩大 SHADOW 的
17 项必需接口集合。接口本身不执行归属调和；上游批量操作可能部分成功，后续协调器必须
先回读实际绑定，不能因为失败响应就假定未产生变更。

候选 `ObserveOwnership` 在读取前后核对实例 GUID、Panel 版本和已审核的精确 OpenAPI 摘要，
并比较两轮对象身份／绑定、模板及完整组装配置。模板摘要包含 outbound test URL；对象列表
顺序和持续变化的计数器不属于身份变化。任一契约、归属或摘要不匹配均不返回部分成功。
这不是原子快照，也不证明当前 Xray 已采用组装配置；写入前还须将回读结果与持久化检查点
比较，并验证实际数据路径。模板和配置读取可能触发上游维护，因此该方法不进入 SHADOW，
只能由明确授权的候选流程调用。

## API、安全与能力握手

3x-ui API 路径没有版本前缀，OpenAPI 元数据也只标识为 `3.x`，因此不能把“HTTP 200”视为
兼容保证。实现以 [官方 API 文档](https://github.com/MHSanaei/3x-ui/wiki/Configuration#api-documentation)
和目标实例实时提供的 OpenAPI 为准，社区 Postman collection 只作辅助参考。每个 Agent 在
接管运行时前必须完成能力握手：

1. 读取 3x-ui 版本和 OpenAPI 文档，记录其摘要。
2. 确认所需路径、方法、认证方式以及关键请求和响应字段均存在。
3. 在隔离对象上执行无损语义探测，包括创建、读取、更新、删除和 Xray 配置读取。
4. 核对运行中 Xray 版本，并用该节点实际运行的内核验证渲染结果。
5. 未通过握手时保持原 provider，不发送成功确认，也不尝试“尽力兼容”。

第一阶段的只读 `SHADOW` 为避免碰触生产状态，只完成第 1 步和第 2 步中的**精确路径/方法
形状检查**，并额外读取一次已存储的出站计数来验证该读取权限；它不验证全部
请求/响应 schema、写路由权限或写入语义，也**不会**调用增删改接口。控制台的`契约就绪`
只表示实时状态、所需路由形状和这次读取均成功，不表示写入语义、计费或数据面已经等价，
更不允许据此进入 `ACTIVE`。认证/schema 深检及第 3、4 步只能在后续隔离对象和金丝雀阶段完成。
实时 OpenAPI 每五分钟重新读取；出站计数权限检查在 Agent 启动或 3x-ui 版本变化时执行。
已核对版本中两条读取都要求 admin scope，但不能据此证明未来版本的配置读写权限；配置
保真和写入验收仍独立保留。SHADOW 的契约测试有固定请求白名单，拒绝配置、模板和显式
写入请求；不能再以主动组装前后配置的方法证明观测无副作用。

进入 ACTIVE 前，CI 必须针对每个受支持的 3x-ui 版本启动官方镜像并运行完整契约测试；该
官方镜像测试矩阵**尚未在第一阶段实现**。升级先经过契约测试与单节点
金丝雀；发现未知 OpenAPI 摘要或缺失能力时拒绝接管。Chiral 不在源码中固定 Xray 版本，
但每次实际安装必须记录解析后的 Xray 版本、3x-ui 版本与镜像 digest，确保该次动作可审计、
可复现、可回滚。

优先使用最小权限 API token。当前 3x-ui 的 `node-sync` scope 不覆盖实时 OpenAPI、完整 Xray
模板、最终 config 读取和 Xray 安装等能力；在上游提供更窄的 Chiral scope 前，可使用仅存于节点的
admin token，但必须同时满足：

- 3x-ui 管理监听只绑定 `127.0.0.1`，不得由 Core 或公网直接访问；
- token 通过显式挂载的普通文件提供，不得授予 group/other 权限（通常用 `0400` 或 `0600`），
  不必位于 Agent 状态目录；
  token 不上报 Core、不写日志、不进入错误正文；
- Agent 使用显式端点白名单和请求体校验，绝不提供通用 API 转发；
- bootstrap 使用随机管理员凭证和随机 base path，接管成功后轮换一次 token；
- 禁用 3x-ui 自带订阅服务和节点间同步，避免第二条管理链路；
- 不需要 IP 封禁时禁用 fail2ban，并移除 `NET_ADMIN` / `NET_RAW` 能力。

Agent 与 3x-ui 必须共享可访问的回环通道。当前隔离验证使用 3x-ui 的 `network_mode: none`，
实验 Core 与 Agent 使用 `network_mode: service:3x-ui`，不发布宿主机端口，也不使用生产网络。
未来接管节点动态 inbound 时可以评估 host network，但必须先完成端口归属核对与迁移评审，
不能将其用于要求不中断生产连接的并行实验。3x-ui 数据库、证书以及 Xray / geofile 目录均应
使用独立持久化卷；容器重建前记录镜像 digest 和实际内核版本，不能依赖浮动的 `latest` 恢复现场。

## 调和与功能等价门槛

本节“等价”以 2026-09-30 用户确认的产品口径为准：近期在线近似值与原版初始化计费缺口是
两项显式接受的差异，不再要求达到完整在线快照或初始化无损计费，但必须如实标注。除此之外的
配置、授权、订阅、数据面和故障隔离要求没有降低。

一个完整配置会拆成 3x-ui 的基础 Xray 模板、多个 inbound 和多个 client API 操作，这些调用
不是数据库事务。Agent 必须按节点串行执行声明式调和，并携带 Chiral 期望版本和规范化摘要：

1. 读取当前受管对象并保存 3x-ui 数据库和最终 Xray config 快照。
2. 计算完整候选配置和计划，只操作有 ownership 标识的对象；候选须保留全部字段。
3. 在不写入持久化期望状态、不停止或替换旧 Xray 的前提下，完成最终配置比较和实际内核
   校验；若原版 HTTP 无法提供这条失败隔离路径，则拒绝接管，不能先改后验。
4. 应用已验证计划。日常用户新增、修改、停用和删除不得额外重启 Xray 或中断既有连接；
   不能以强制重启规避热更新字段丢失。
5. 回读 3x-ui 生成的最终 config，并用与订阅相同模板和真实凭证执行端到端数据探测；进程
   存活或 API 可响应不等于可用。
6. 全部通过后才发送 `ConfigAck(applied=true)`；任何失败都必须保持旧运行态继续服务并上报
   明确阶段。尚不能证明这一点时保持 SHADOW，不把补偿尝试当作等价保证。

除上述两项已接受差异外，以下当前接管要求全部通过后才可把节点标为等价：

- 任意骨架、inbound、outbound 与 routing 的表达力，包括 xhttp 上下行分离、后量子密钥、
  REALITY、中转线路、外部出口和受限目的地规则；
- 每个 `用户 × Profile × 节点 × 出口` 的独立凭证、启停、到期、配额与自动续期；
- xray JSON、v2rayN、mihomo 和 Stash 的所有订阅输出逐字节不变；
- 全部配置字段保留；日常用户操作不产生 direct-Xray 原本没有的 Xray 重启或连接中断；
- 失败候选配置不改变持久化期望状态和旧运行态，旧服务继续承载真实数据；
- 节点、用户、inbound、outbound 和出口维度的已观测流量按倍率只计算一次；初始化首批基线
  缺口按已接受的原版口径保留，不估算或伪造补账；
- 在线信息仅展示为近期用户／IP 的近似观测，明确标注不完整；不得发送 `complete=true`、把
  近期记录称作当前在线集合，或把没有记录称作无人在线；
- 配置版本、审计、告警与真实数据路径探测保留原有语义；普通在线更新按节点串行。明确失败
  只在既有安全条件下最多自动恢复一次当前磁盘版本，无法确认时有界只读核对后转人工；
  预安装不激活与离线内核回滚按用户决定暂缓。

3x-ui 的流量值按累计计数读取，Agent 不调用会改变配额语义的 reset API。只读取本节点的
`inbounds/list` 中 `clientStats`，不使用可能叠加主面板汇总的用户列表流量；同一统计对象
去重，inbound / outbound 仅作独立遥测，不再次计入用户配额。`total` 为配额，不是流量。

Agent 为每个外部键持久化 watermark 与 runtime epoch。普通轮次取累计差；任一方向下降时
视作新计数周期，两方向均从当前值起算。已知数据库恢复或实例身份变化时重新建立基线，明确
上报连续性不确定，不能把历史累计值直接再计费。仅凭累计计数无法识别所有数据库回退，也
无法恢复上游在两次采样之间清除的字节；可靠投递不能被描述为解决了这些采样缺口。

用户已接受上述原版采集口径作为 3x-ui provider 的计费定义：新采集对象的首批非空计数只
建立基线，基线前字节不可恢复。缺口上限未知，也不能承诺每次都能检测或记录连续性事件；
不得估算、补写或以探针预热掩盖。该已知差异不再单独阻塞接管，但基线建立后的可观测增量
仍须去重、可靠投递并正确归属，撤权或删除也不得造成重复计费、恢复访问权或错记到自然人。

每次采样的全部 delta 与新 watermark 原子落盘，并按协议限制分批。Agent 在 Core 明确发送
`StatsPolicy` 后才投递带 `reporter_id` / `sequence` 的批次；每批收到精确 `StatsAck` 前内容
不变、重试身份不变。Core 将凭证计数、用户倍率用量、图表、inbound / outbound 遥测和去重
收据放在同一事务中，提交后才确认。ACK 丢失时重放不重复计费；超过边界或跨节点凭证整批
拒绝。旧格式保留兼容，但不能绕过所属节点检查。共享上限为每批 4096 条、名称 512 字节，
确保最大消息仍小于默认 gRPC 接收限制。旧 Core 未协商时不读取新 provider 的待投递账本。

新旧计费路径均按每条凭证增量、十进制倍率乘积向上取整一次。倍率沿用现有 SQLite REAL /
JSON number 存储，以该值可往返还原的最短十进制表示参与精确有理数运算；不使用浮点乘法
或 epsilon 修补。这样 `100 × 1.1` 精确计为 `110` 字节，1 倍倍率也不会丢失超过 `2^53`
的整数精度。计费和原始累计计数溢出时事务失败，不允许 SQLite 将整数累计提升成浮点值。

连续性不确定不是一条可丢弃的日志：它作为不含计费 entries 的独立批次参与摘要和确认，
Core 将固定原因与批次身份写入 `stats_continuity_gaps`，与回执同事务提交。后续普通批次推进
回执水位也不会删除历史缺口；事件队列满、ACK 后断线不能让缺口证据消失。

迁移 `0030` 尚未发布，开发阶段曾应用较早内容的临时数据库应重新创建，不能复用迁移号
来推断 schema 已完整。旧实验账本中已经持久化且超限的 pending 批次也不会被静默改写：
读取明确失败并保留原文件，避免以相同 delivery ID 发送不同内容。这些限制不涉及已部署生产库。

切换前仍应让原 provider 完成最后一次增量上报，再以 3x-ui 当前值建立基线，以尽量缩小但
不能宣称消除已接受的初始化缺口；并须验证用户删除、计数重置和实例恢复后不重复、不串户。
当前接口与投递基础设施尚未接入 ACTIVE 3x-ui provider，不能据此宣称生产计费已经接线完成。

2026-09-29 的 [本机官方 HTTP 写入与数据面验证](../deploy/3x-ui-lab/validation-write-20260929.md)
已确认基础模板读写及后续请求计费可用，但冷启动首次真实请求未计入 HTTP 用户计数，受管
client 的合法 `level` 字段也未保留。该次整体契约测试的历史结论仍为 FAIL；此后用户接受
冷启动首批漏计作为已知计费口径，但 `level` 字段丢失，以及以重启规避它会额外中断连接，
仍不具备生产接管条件。不得用预热后的计费通过掩盖首次采样损失，也不得将单一受管 client
路径失败夸大为所有官方 HTTP 配置途径均不可用。

### 近期近似观测的候选实现（2026-09-30）

窄类型 HTTP 读取器分别调用官方 `onlinesByGuid` 与 `clientIpsByGuid`，只采纳已核对的
本机 Panel GUID 和调用方明确提供的受管凭证清单；不得把响应中的下级节点归属到当前节点。
读取前后检查实例身份，所需两个接口属于候选可选能力，不扩大 SHADOW 自动观测白名单。

候选 runtime 可通过独立 `RecentOnlineReporter` 接口返回缓存用户和近期地址。Agent 仅在
本条连接明确协商支持后发送 `RecentOnlineReport`，不会回退为 `OnlineReport` 或生成
`complete=true`。报告限定用户和地址数量；读取失败明确为未知，策略撤销或连接取消后
丢弃结果。Core 再次验证节点凭证归属并单独保存近似信息，不将其计入实时地址数量、设备
阈值或真实连接历史。记录的获取时间不能用作最后在线时间。

管理端分别展示实时观测与近期近似信息；空缓存、空地址、失败和过期均不能解释为离线。
具体地址继续受原有超级管理员权限和读取审计保护，普通列表只提供汇总，不扩大门户权限。
该实现尚未接入可写 3x-ui runtime，不改变现有 direct-Xray／SHADOW 行为；本地合成契约与
单元验证不代替官方实例的端到端观测验收，也不解除 ACTIVE 闸门。

冷启动漏计同样有明确范围：官方流量采集对象的 `StatsLastValues` 为空时，第一批非空
计数仅建立基线，不产生增量；空采样不能完成预热。Panel／采集对象重建会触发此路径，
不能笼统断言每次单独重启 Xray 都会清空同一采集对象。官方 HTTP 中尚未发现能补回该
首批计数的接口；Chiral 后续可靠投递不能恢复此前已被丢弃的数据。用户已接受该缺口，且
明确其上限未知、不能假定每次都能检测；实现与文案必须保留这一不确定性，不能声称无损。

### 配置保真与 HTTP 数据探测候选组件

离线 [`agent/cmd/3xui-audit`](3x-ui-compatibility-audit.md) 已用于盘点单份完整 Xray JSON 中
已知的 `level` 路径风险和需要额外审查的未知字段。它只读标准输入，不连接节点、3x-ui 或
数据库，输出不含凭证，并始终返回 `takeover_permitted=false`；没有发现已知问题也只表示
仍需运行验收。本轮没有安全的静态生产配置语料，未读取 `data/chiral.db`，因此工具交付不算
生产配置覆盖或接管证据。

`CompareConfig` 比较完整期望配置与官方最终配置，忽略对象键顺序与空白，但保留数组
顺序、数值原始表示以及缺失／null／false 的差异；不跳过 api、stats、policy 或未知字段。
重复键、无效编码、过深或过大的输入直接拒绝。结果只返回摘要、固定顶层分类和路径哈希，
不记录私钥、凭证、原始键路径或配置正文。通过只证明回读保真，不证明 Xray 已接受并应用。

候选 `ProbeOutbound` 仅调用官方 `testOutbound` 的 `real` 模式。使用前独立检查可选
`outbound_probe` 能力，不扩大已有 17 项 SHADOW 门槛。显式目标 URL 必须与 3x-ui 设置
前后回读一致：官方接口不读取表单中的目标 URL，客户端不得虚构该参数或隐式更改设置。
返回必须具有外层成功、嵌套成功、匹配 tag、`real` 模式及 200–399 HTTP 状态；只验证 TCP、
直接出站、上下文以同 tag 偷换被测出站均不能当作节点代理成功。

前后回读并非原子锁，调用方仍需独占配置调和并核对节点凭证、实例与运行版本。模板读取
可能触发上游遗留存储修复，因此该组件不用于 SHADOW。调用方超时不会保证上游临时测试
进程立即停止，不自动重试。组件尚未接入 ACTIVE 或更新协调器，不能据此宣称真实更新
探测已验收；也不能证明返回正文逐字节一致或被测内核摘要。

同日的 [原始模板候选投影实验](../deploy/3x-ui-lab/validation-projection-20260929.md) 验证
了另一官方路径：完整 raw inbound/client 保留在模板，停用的同 tag 对象仅作计费索引。
这组配置能够完整回读，基础连接授权与后续计费可用，但两轮历史结果仍整体 FAIL：冷启动漏计，
全新 `level:3` 用户能传输正文却没有用户计数。官方热差异调用 AddUser 时没有设置 Level，
与该现象一致；模板中的字段保留不能替代运行行为验证。首批漏计现已作为已知计费口径接受，
但字段保真问题仍未解决。该方案尚未采纳，不得以强制重启后的成功宣称热更新等价，也不得
以额外中断换取字段保留。新 HTTP 探测器不在
该投影实验的数据面证据之内；它随后已完成单独的
[官方 HTTP 探测与恢复验收](../deploy/3x-ui-lab/validation-http-probe-20260929.md)：200/204
命中隔离源站，错误凭证官方明确失败，500 被 Chiral 拒绝；作为候选更新探针时，明确安装
失败及回应丢失三个场景也通过。后者安装返回为测试注入，不下载内核；探测和恢复均调用
原版 HTTP，不由 Agent 启动测试内核。这不改变已接受的计费／在线近似边界，也未启用生产调度。

这些差异不能由 Chiral 的 HTTP 重试、累计计数账本或数据库备份自动补齐。预安装不激活、
离线内核回滚、完整在线快照和初始化首批无损计费均不再单独作为当前阻塞依据；后两项必须
如实标成近似或有缺口。配置全字段保真、日常用户操作无额外中断、失败配置不影响旧运行态
等其余未通过项仍然有效。节点级迁移回退到 direct-Xray 是另一条保留路径，不等同于 3x-ui
provider 自身完成离线内核回滚。继续保持 ACTIVE 关闭；普通更新的源码可行性不证明整个迁移
已经完成。

  credential，而 `core/internal/profile/enforce.go` 明确只保证入队，不保证节点已完成。
  `core/internal/store/stats_batch.go` 的现有策略不会将未知／已撤销凭证计入用户额度。
  因此，解绑后迟到的批次可能仅进入节点历史；可靠 ACK 并不恢复已删除的归属。
  接入前需设计撤权与最终计费确认的顺序或专用计费归属保留机制，不能为计费保留有效访问权，
  也不能简单将所有未知 email 重新计入自然人。此项为静态调用链证据，尚未交付修复。

现阶段不得把候选原语直接接到 `Runtime.Apply`／`AddUser` 并据 HTTP 成功返回生产确认。
继续编写只能在模拟接口或缩减字段下通过的调和器，不能证明原始目标已经推进到可接管状态。
Mai 已明确接受近期在线近似值和原版初始化计费缺口；这两项差异不再要求通过修改上游补齐，
也不再单独阻塞接管。该范围调整不涵盖字段丢失、用重启弥补日常用户变更、失败配置扰动旧
运行态或其他未完成能力。既有 direct-Xray 节点、访问授权、订阅与数据保持不变，生产接管
继续关闭；不恢复任何增强分支授权。

首次开放的有限组合现已通过 [独立隔离实验](../deploy/3x-ui-lab/validation-bootstrap-20260929.md)：
先仅开放私有探针，以实际 HTTP 计费增量确认预热，再增加完整的新用户入站，用户第一笔
唯一请求的 51,200 字节正文计入该用户名下，探针计数不变。原始首批漏记没有被修复，
而是限制为测试字节；该记录不是 ACTIVE 接线验收。用户现已接受采集对象初始化时的基线
缺口，包括既有用户在 Panel／采集对象重建后立即恢复时可能丢失的首批计数，但不能据此
假定缺口有固定上限或每次可检测；该选择也不抵消同入站热增用户的 Level 缺口。
单独 Xray 重启不一定清空同一个采集对象，必须区分服务实例与计数周期；HTTP 返回的
`appStats.uptime` 来自 Xray 进程，不能作为采集对象的代次标识。该组合未接入生产逻辑。

稳定 ownership、本地状态与失败关闭组件已实现但未接入完整调和；跨升级日志及外部写入者
的单写者协调和配置失败补偿仍未完成。重新配置入站或额外
增加一个 3x-ui 验证实例则是未经确认的方案，不能假定它们不扰动连接、等同实际节点
预校验。在线完整快照与初始化计费缺口已经按明确降级口径接受；配置全字段保真、日常用户
操作无额外中断、失败配置不影响旧运行态以及其余接线和运行验收完成前，仍不启用通用
ACTIVE provider。预安装不激活与离线内核回滚仍按用户决定暂缓。

### 普通在线更新的候选流程

以下基于官方 3.8.5 的源码核对、Chiral 候选实现和 2026-09-30 的隔离实验。第 05 次实验
已完成一次真实 v26.9.8 安装与重建持久性验证；其 v26.9.9 更新及第 06 次 v26.9.8 安装均
没有取得确定终态，因此下列流程仍未整体通过：

1. Core 决定更新策略和目标版本，Agent 查询 `GET /panel/api/server/getXrayVersion`。
   该接口返回可安装版本列表，不是当前运行版本，也不是自动更新策略。
2. Agent 按节点串行调用 `POST /panel/api/server/installXray/:version`。原版执行联网下载、
   SHA-256 校验、替换与重启；Chiral 不自行管理内核文件。
3. 读取 `GET /panel/api/server/status` 的 `xray.state` 与 `xray.version`，再验证实际代理
   数据路径。HTTP 成功、版本匹配和真实业务可用是不同层次的证据。
4. 出错时停止扩大更新并记录失败。超时只能说明请求结果未知，不能证明安装已经结束；
   必须先确认运行状态，避免与仍在进行的安装重叠。恢复也仅能使用原版 HTTP API，且应
   独立验证结果，不承诺离线恢复或自动回滚成功。若无法确认安装已结束，应保留结果未知
   并阻止后续冲突操作；仅一次状态读取不能充当安装任务已终止的证明。

普通更新会中断该节点已有连接，安装后的容器重建持久性及超时恢复仍需隔离验证；本次
需求调整不构成在 Turin 执行更新的授权。3x-ui 面板自身更新与 Xray 内核更新是两条独立路径。

已核实的实现约束：

- 安装先标记手动停止，再下载和校验；下载失败后不会由崩溃看护自动启动。完整的官方
  `success:false` 回应说明该次同步安装已返回，但不说明失败阶段。候选协调器在同一实例
  连续报告停止或错误时，最多调用一次 `restartXrayService` 启动当前磁盘版本；已运行时
  只验证，不为恢复而再次重启。停止状态附带的版本是旧进程的缓存，不能证明磁盘仍是旧版。
- `/status` 由后台约每两秒更新，状态与版本不是原子采样，也不返回采样时间。候选流程以
  有界轮询容忍正常缓存延迟，但不把等待两秒等同于新鲜度保证；恢复后仍须核对实际运行
  版本和新建连接的真实代理数据路径。该恢复不是离线回滚，也不保证启动的是旧内核。
- HTTP 服务写超时为 30 秒，下载客户端超时为 60 秒，校验文件另发请求；安装使用独立的
  后台上下文。官方提交 `7ef22f94c950ff09f0870e2295fa65ad5968742c` 的
  `internal/web/web.go` 第 651 行设置 30 秒 `WriteTimeout`，而 `internal/web/service/server.go`
  的 `downloadXRay` 使用 60 秒 HTTP client。第 05 次脱敏上游日志已出现下载
  `context deadline exceeded`，说明明确失败响应可能在 handler 写回前丢失。因此安装可能在
  调用方超时后继续执行，也可能已经失败但 Chiral 收不到终态；两种情况都不能直接重试、
  推断进程已停止或触发恢复写入。
- 下载必须有不依赖被更新 Xray 的出网路径；若管理请求此前通过本机 Xray 出口，停机后
  上游会回退直连，版本查询成功并不能证明后续归档下载可达。
- 隔离运行器可显式选择实验专用 `--proxy-dns-over-tls`。该模式只改变新建 CONNECT 代理，
  固定直连 `1.1.1.1:853`，使用 SNI `one.one.one.one`、TLS 1.2 或更高版本并验证证书，失败时
  不回退明文 DNS；运行器只把该代理的容器 DNS 设为 `127.0.0.1` 以封闭环境解析兜底。此选项
  默认关闭，并与 `--proxy-dns 1.1.1.1` 互斥，不修改宿主、Docker daemon、应用实例、3x-ui
  或生产 DNS。这是实验出网条件，不是产品运行时 DNS 设计。
- 官方 Docker 默认内核目录为 `/app/bin`，官方 compose 没有持久化该目录。容器重建时
  会丢失通过 API 安装的版本；迁移部署须为 3x-ui 独立持久化该目录并验证重建行为，不把
  该目录挂给 Agent，也不借此实现已禁止的 Agent 内核管理或离线回滚缓存。

#### 当前候选实现的边界

`agent/internal/threexui` 的 `XrayVersions` 保留上游精确版本标签，`InstallXray` 只发一次
请求，不暗中重试。安装结果分为未发出、明确失败和结果未知；只有完整成功响应加目标版本
与真实数据面验证才能判为更新成功。非成功 HTTP 状态或不完整响应不能证明上游安装已经
结束；可以继续只读核对服务现状，但不能据此发起另一项安装或恢复重启。

`OpenXrayUpdates` / `Run` 在安装请求发出前将操作记录原子落盘并同步，使用私有文件锁
防止同一记录路径被多个进程同时操作。操作 ID 及其完整请求内容的摘要一起保留，同 ID
重放只返回历史结果，同 ID 改参数则拒绝。超时、断线或 Agent 重启均不会使未知请求重新
发送；`Observe` 只读，观察到目标版本也不会将未知任务自动判为结束。`Reconcile` 核对原
请求摘要，只处理最后一项未完成核验的操作，可在 Agent 重启后继续收集证据。明确成功
回应之后，有界等待状态刷新并匹配预期实例、运行版本，通过调用方提供的真实数据面探测
后，才能得到 `verified`。缺少探测不能当作成功。

明确安装失败时，`Run` 自动尝试一次有界恢复；请求调用方取消不会使已确认失败的恢复
立即中断，但独立恢复上下文仍有时间上限。只有实时能力握手及同实例连续停止观测通过，
才会在重启派发标记持久化后发送恢复请求。派发后崩溃或丢失恢复响应时，只读核对，永不
重复重启。持久化失败、身份变化、状态未知均不得触发恢复写入。

安装丢失结果时，`Run` 自动进行有界只读核对，`Reconcile` 可继续核对；不盲目重装、不
与可能仍在执行的安装争抢进程。服务可达、观测到的运行版本、恢复请求是否发出均独立
记录。即使目标版本已可用，安装结果仍保留 `unknown`；即使恢复成功，原安装失败仍保留
`failed`。服务可用不冒充更新成功，也不自动解除下一次更新的限制。

每轮恢复或核对默认最多 30 秒，轮询间隔为 2.5 秒，单次探测最多 3 秒，重启前的防误重启
探测最多 2 秒，避免探测耗尽整个恢复机会。服务证据包含本地观测时间；历史重放不是当前
健康检查。本地记录锁不能阻止管理员或另一程序直接调用官方 API；上游没有原子条件重启，
运行这些流程时必须确保同一实例没有其他写入者，不宣称已解决跨控制器竞态。

记录只保存操作摘要、版本、固定原因及恢复与服务观测，不保存 token、配置、探测凭证或
上游错误正文。旧记录的请求摘要和防重复派发状态必须保留，不得因格式扩展清空记录。
调用方必须提供预先建立且持久化的私有状态目录，并始终复用同一文件路径；文件缺失、损坏
或超限时拒绝继续，不删除重建。当前最多保留 128 个操作记录，不自动淘汰。尚未发出安装
的失败允许以新操作 ID 再试，但未知、已执行失败或验证不充分的结果会阻止后续自动更新。
人工消除不确定状态与记录安全归档尚未实现，不得以删除记录解除限制。

这些组件不实现旧 `runtimeprovider.Upgrader` 的预安装与离线回滚承诺，也没有把 SHADOW
变为可写模式。模拟 HTTP 故障测试不等于官方实例安装、容器重建或完整生产升级验收。
独立真实实验现已取得 v26.9.8 安装、更新前数据面、配置／凭证保持和一次重建持久性的
明确 PASS；v26.9.9 更新结果仍为未知，更新后重建未执行。调度接线、成功目标更新路径与
更新后数据面验收仍是后续工作；未知结果按既定人工闸门保留，部分阶段证据不能冒充四阶段
整体通过。

已在全新本机官方实例通过三项恢复故障注入验收：明确失败、恢复回应丢失及安装回应丢失，
均验证新连接的实际字节和操作不重复。见
[恢复验证记录](../deploy/3x-ui-lab/validation-update-recovery-20260929.md)；注入的安装响应
不代表已执行真实 release 下载，且此结果不抵消配置保真、失败隔离和生产接线等未通过门槛。

## 分阶段迁移

### 1. 基础设施

- 引入 provider 接口，原生 provider 仍为默认值。
- 实现窄类型的 3x-ui client、能力握手、契约测试和敏感信息脱敏。
- 以增量协议字段上报 provider、3x-ui 版本、OpenAPI 摘要、Xray 已安装/运行版本和兼容状态；
  旧 Core 与旧 Agent 必须仍可互通。

### 2. 影子验证

离线全用户订阅与节点配置比较工具见[使用说明](offline-equivalence.md)。它仅接受静态
数据库副本，使用固定时间和现存凭证，不启动 Core 或执行迁移；其合成测试不替代生产
语料验收。真实在线更新的受限出网及重建验收方案见
[独立实验计划](../deploy/3x-ui-lab/real-upgrade-plan.md)。2026-09-30 的六次运行整体均为
`INCOMPLETE`，其中第 05 次有两个完整阶段 PASS；详见
[验证记录](../deploy/3x-ui-lab/validation-real-upgrade-20260930.md)。

- 使用独立 Core、Agent 和 3x-ui 进行隔离验证，入口见
  [`deploy/3x-ui-lab/README.md`](../deploy/3x-ui-lab/README.md)。实验使用新数据卷和凭证，
  不重建生产容器、不复用生产节点身份，也不接管生产 inbound。
- 将同一 Chiral 期望状态投影到 3x-ui，读取最终 config，与原生 provider 的配置做语义对比。
- 用真实配置语料覆盖全部传输、密钥、线路和路由组合，并比较所有用户、所有客户端格式的
  订阅输出。

### 3. 单节点金丝雀

- 用 SQLite `.backup` 备份 Chiral 数据库；停止写入后备份并验证恢复 3x-ui 数据库。
- 记录原 provider、配置版本与摘要、Xray 版本/二进制、3x-ui 镜像 digest、token id、端口和
  防火墙状态。
- 刷新原 provider 的最后一批流量，建立 3x-ui watermark 基线，尽量缩小并记录已接受但无法
  保证消除或完整检测的初始化缺口。
- **先停止原生 Xray，再启动 3x-ui 管理的 Xray**，避免同端口双实例；保持原凭证和端口。
- 要求配置读取、内核测试、真实订阅者数据路径、Core 健康检查和 Agent ack 都给出正向成功
  信号，并再次逐字节比较全部订阅输出。

### 4. 扩大与收尾

逐节点推进，每一批都保留观测窗口。原生 provider 和旧状态至少保留一个完整发布与回滚周期；
删除原生实现、改变默认 provider 或开放 3x-ui 管理入口都必须另行评审，不能夹带在首个集成
变更中。

## 回滚

任何能力握手失败、配置差异、计费异常、真实数据路径失败或 Agent 未确认都触发节点级回滚：

1. 阻止新的调和操作，保存 3x-ui 数据库、最终 config 和日志供诊断。
2. 停止 3x-ui 管理的 Xray，确认监听端口已经释放。
3. 把节点 provider 切回原生，恢复记录的旧 config、Xray 二进制和 Agent 状态。
4. 启动原生 Xray，重推旧配置内容作为一个新的 Chiral 配置版本。
5. 用真实凭证完成数据路径探测，确认 Agent ack、全部订阅输出，以及计费没有重复或串户；
   初始化缺口仍按已接受口径记录，不伪称连续无损。

绝不允许两个 provider 同时管理同一组端口，也不以恢复 3x-ui 数字 ID 作为回滚成功条件。
回滚的完成标准是客户数据路径恢复、Core 收到明确确认、订阅保持不变，且计费符合当前已接受
口径并未发生重复或串户；不能以“计费连续”掩盖初始化缺口。
