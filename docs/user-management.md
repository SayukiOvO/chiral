# 用户管理、流量与订阅

## 用户模型

用户通过管理 Xray-core 配置里的 `clients` 数组实现。不同用户能访问的 inbound 不同，需做区分。

> **「用户」在本文里指代理用户**——`users` 表里的一行，有配额、凭证和订阅链接。它可以由管理员手工创建，此时这个人**没有登录能力**。
>
> 端用户的**登录身份**是另一张表（`user_accounts`），行不存在就是「这是管理员建的、不能登录的代理用户」。注册、会话、门户能看到什么，见 [user-portal.md](user-portal.md)。

## 凭证唯一性：强隔离（已定）

**每个用户在每个 inbound 上都用独立凭证**，而非一套凭证跨 inbound 复用。凭证是 `用户 × Profile × 节点` 粒度：同一用户在不同接入点的 UUID / password 各不相同。

- **好处**：任一凭证泄露只影响那一个接入点，可单独吊销、单独定位泄露来源、单独限速。
- **代价**：要管理和下发的凭证更多、`clients` 数组更大——这些由 Core 统一生成与跟踪，对用户透明。
- **统计键**：每凭证独立的 `email`（形如 `用户名@接入标识`），从而精确到「用户在某接入点」的流量。用户总流量 = 其名下所有凭证流量之和。

## 运行时增删不重启

启用 / 停用、到期、超量封禁，通过 Xray-core HandlerService 的 `AddUser` / `RemoveUser` 在线增删 `clients`，不重启 Xray-core。只有 inbound / outbound 结构本身变化才需 reload。

## 限制与统计

每个用户三个约束：**流量配额、到期日期、是否自动续期**。

- 超配额或到期 → Core 令相关 Agent 在线移除该用户在各接入点的凭证，用户降为不可用。
- **自动续期**：到期时按周期顺延到期日并清零已用流量（周期可配，如按月）。
- **流量统计**：Agent 定期读 Xray-core stats 上报**增量**，Core 累加。必须处理 **Xray-core 重启导致计数器归零**——上报增量而非绝对值，或 Agent 侧记上次读数做差值，避免统计跳变。

## 订阅链接

每个用户一个 `https://panel/sub/{token}`。客户端类型识别两条路：
1. URL 后缀显式指定 `?client=clash`（优先）。
2. 否则按 `User-Agent` 猜测（clash/mihomo、v2rayN、stash 等 UA 各有特征）。

命中后用对应客户端模板渲染，填入该用户的独立凭证。

> **订阅 token 现在是可恢复存储的**（M5，推翻 0003 迁移注释里「从不存储」的原决策）。`users.sub_token_enc` 用 AES-GCM 密封，AAD 绑定行；`sub_token_hash` 与查找路径一个字节未变。
>
> 理由：门户的核心价值之一就是随时能看到自己的链接，而「只能重新生成」会炸掉用户已配置的所有客户端。代价说清楚——从「我们想拿也拿不回」降级为「持有 `CHIRAL_SECRET_KEY` 就能拿回」。配套硬约束：门户开启且无该密钥时 Core 拒绝启动。

### 四种客户端现实情况

| 客户端 | 输出格式 | 说明 |
|--------|---------|------|
| **xray** | config.json | 最完整，直接给 xray 客户端配置 |
| **v2rayN** | `vless://` 或 JSON | 可跑 Xray 内核，分享链接或 JSON 都行 |
| **clash(mihomo)** | YAML | vless/reality/vision 支持好；xhttp 分离、后量子等前沿特性能否完整支持要看其当前版本 |
| **stash** | YAML | clash 兼容核，情况类似 mihomo 但更保守 |

因各客户端能力参差，「每客户端手写模板」的思路是对的——能力不足的客户端在其模板里降级，或只输出它支持的那部分节点。
