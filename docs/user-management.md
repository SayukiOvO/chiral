# 用户管理、流量与订阅

## 用户模型

用户通过管理 Xray-core 配置里的 `clients` 数组实现。不同用户能访问的 inbound 不同，需做区分。

> **「用户」在本文里指代理用户**——`users` 表里的一行，有配额、凭证和订阅链接。它可以由管理员手工创建，此时这个人**没有登录能力**。
>
> 端用户的**登录身份**是另一张表（`user_accounts`），行不存在就是「这是管理员建的、不能登录的代理用户」。注册、会话、门户能看到什么，见 [user-portal.md](user-portal.md)。

## 凭证唯一性：强隔离（已定）

**每个用户在每个 inbound 上都用独立凭证**，而非一套凭证跨 inbound 复用。凭证是 `用户 × Profile × 节点` 粒度：同一用户在不同接入点的 UUID / password 各不相同。

- **好处**：任一凭证泄露只影响那一个接入点，可单独吊销、单独定位泄露来源、单独限速。
- **代价**：要管理和下发的凭证更多、`clients` 数组更大——这些由 Core 统一生成与跟踪，对用户透明。
- **订阅名称**：订阅者在客户端里看到的配置名，取自下载文件名。默认 `chiral`，在控制台「设置」里改；改动对之后每次拉取生效，已导入的客户端要重新导入才会改名。
- **统计键**：每凭证独立的 `email`（形如 `用户名@接入标识`），从而精确到「用户在某接入点」的流量。用户总流量 = 其名下所有凭证流量之和。

## 按用户指派节点

授权是按接入配置给的：绑一个 Profile，这个人就拿到该 Profile 绑定的**每一个**节点。这是对的默认值，但它没有留下「这个人可以用这些机器、不能用那台」的余地。控制台「用户 → 可用节点」是这条例外，自有节点和外部节点在同一处勾选。

**新建的订阅者什么都没有**：没有接入配置，也没有任何外部节点。接入配置本来就是要授予的（没绑就渲染出空订阅），但外部节点前面没有 profile 挡着，于是「还没决定」和「把我们从任何人那儿买来的东西全给他」是同一个状态。现在这两半都得有人点头。

**存的是拒绝，不是授予。** 这个方向不是随手选的：新绑上来的节点，或新加进来的外部来源，如果要逐人授予才可见，那么每加一台机器就要回头去改每一个用户，而漏改的表现是「这个人的订阅里少了一台」——没有报错，没人会发现。存拒绝则新节点立刻对所有人可见，存量订阅者一个不受影响，只有被明确点掉的那一条是特例。

两条边界：

- **取消不等于吊销凭证。** 凭证还在节点上，只是不再渲染进这个人的订阅。要真正断掉，取消对应的 Profile 授权。
- **没有权限的节点照样显示，只是灰着。** 一个节点如果不在这个用户任何 Profile 的绑定里，勾上它也不会有任何效果——这种时候摆在那里灰掉，比干脆不显示要好：「我的节点去哪了」是更难回答的问题。

**中转线路是第三类，有自己的一张拒绝表。** 「能直连出口吗」和「能经入口去出口吗」是两个独立的答案，而跑中转的理由通常正是前者为否。新建的线路默认谁都不能用；拒绝了入口节点，经它的线路一起消失——一条经某台机器的线路就是那台机器的地址加一份能用的凭证。

外部节点不挂在 Profile 下（没有 Profile 可挂），所以对它们而言这里就是唯一的开关。同一份数据在「外部节点」页上还有一个从节点看人的入口（每个节点的「谁能用」），两边写的是同一批行。

**取消一个自有节点，会连带取消所有链经它的外部节点，并且是传递的**——链经那个外部节点的下一跳也会一起走。这是有意的，不是遗漏：外部节点的 `dialer-proxy` 指名一个自有节点，那个名字如果不在文档里，整份配置在 mihomo 里加载不了；而把它改成不链直发，等于把订阅者直接甩给对方机场——正是这个设置要防的事。所以链断了就整条不发。受影响的节点在控制台上会灰掉并标出它**直接**失去的那一环，顺着看就能找到断点。

## 流量倍率

节点和外部出口各有一个倍率，默认 1。**它作用于配额，不作用于计数器**：`credentials` 里存的永远是 Agent 量到的真实字节，而 `users.used_bytes`——配额比对的那个数——累加的是计费额。两者合成一个数的话，「他用了多少」和「他该扣多少」就都答不上来了。

用哪个倍率，取决于订阅者在客户端里点的是哪条线：**被中继的凭证按出口的倍率**（字节确实从对方的线路出去，付钱的是那条线），**走中转线路的按线路的**，其余按节点的。计费额向上取整，所以倍率大于 1 时永远不会比实际字节少。

中转线路（自有节点经自有节点）只在**入口**计一次费——那是订阅者认证的地方；线路自己在出口上那份机器凭证不属于任何人，也不进任何人的配额。详见 [node-relays.md](node-relays.md)。

控制台上，节点的倍率在「节点设置」里，出口的在「外部节点」页那一行；用户展开后的「按出口用量」把实际用量和计费额并列，倍率不为 1 时才显示箭头。

## 运行时增删不重启

启用 / 停用、到期、超量封禁，通过 Xray-core HandlerService 的 `AddUser` / `RemoveUser` 在线增删 `clients`，不重启 Xray-core。只有 inbound / outbound 结构本身变化才需 reload。

## 限制与统计

每个用户三个约束：**流量配额、到期日期、是否自动续期**。

- 超配额或到期 → Core 令相关 Agent 在线移除该用户在各接入点的凭证，用户降为不可用。
- **自动续期**：到期时按周期顺延到期日并清零已用流量（周期可配，如按月）。
- **流量统计**：Agent 定期读 Xray-core stats 上报**增量**，Core 累加。必须处理 **Xray-core 重启导致计数器归零**——上报增量而非绝对值，或 Agent 侧记上次读数做差值，避免统计跳变。

## 订阅链接

每个用户一个 `https://panel/sub/{token}`。客户端类型识别两条路：
1. URL 后缀显式指定 `?client=clash`（优先）。
2. 否则按 `User-Agent` 猜测（clash/mihomo、v2rayN、stash 等 UA 各有特征）。

命中后用对应客户端模板渲染，填入该用户的独立凭证。

**看链接不会换链接。** 控制台上点「订阅链接」是**读**，读多少次都是同一条；换成新链接是对话框里单独一个动作，还要再确认一次。

这两件事一度是同一个请求：控制台没有只读路径，想给运维看一眼链接就只能重新签发一条，于是「他的链接是啥」和「把他所有已配置的客户端全弄坏」是同一个按钮。token 从 M5 起就是可恢复存储的，缺的只是这个 handler。

读链接会记进审计日志——它是一份能用的凭证，谁看过值得事后查得到。守卫是 `requireWrite` 而不是 viewer 档，理由和 `config/preview` 一样：返回的东西直接能用。

拿不回来的情况只有两种：这一行早于可恢复存储，或者密钥换过了。这时控制台会明说「找不回，只能重置」，而不是默默给你签一条新的。

> **订阅 token 现在是可恢复存储的**（M5，推翻 0003 迁移注释里「从不存储」的原决策）。`users.sub_token_enc` 用 AES-GCM 密封，AAD 绑定行；`sub_token_hash` 与查找路径一个字节未变。
>
> 理由：门户的核心价值之一就是随时能看到自己的链接，而「只能重新生成」会炸掉用户已配置的所有客户端。代价说清楚——从「我们想拿也拿不回」降级为「持有 `CHIRAL_SECRET_KEY` 就能拿回」。配套硬约束：门户开启且无该密钥时 Core 拒绝启动。

### 四种客户端现实情况

| 客户端 | 输出格式 | 说明 |
|--------|---------|------|
| **xray** | config.json | 最完整，直接给 xray 客户端配置 |
| **v2rayN** | `vless://` 或 JSON | 可跑 Xray 内核，分享链接或 JSON 都行 |
| **clash(mihomo)** | YAML | vless/reality/vision 支持好；xhttp 分离、后量子等前沿特性能否完整支持要看其当前版本 |
| **stash** | YAML | clash 兼容核，情况类似 mihomo 但更保守 |

因各客户端能力参差，「每客户端手写模板」的思路是对的——能力不足的客户端在其模板里降级，或只输出它支持的那部分节点。
