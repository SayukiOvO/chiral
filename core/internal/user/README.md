# user — 用户与凭证

订阅者的准入判定、**强隔离**凭证的铸造（`用户 × Profile × 节点` 各自独立的 UUID / password），以及供 client-entry 模板引用的 `user.uuid` / `user.password` / `user.email`。数据模型在 [`../store`](../store)，本包只放判定与铸造逻辑。

## 关键决策

- **`Allowed` 定义为 `Reason(...) == ""`，只有一份实现。** 门户要告诉客户是**哪一条**卡住了（停用 / 到期 / 超配额），而不只是「有一条」。若门户另抄一份条件，加第四条的那天两边就会分叉。条件重叠时的顺序也是刻意的：运营方主动停用比「顺带也把配额用完了」更值得说，所以 `suspended` 排在最前。
- **被停用的用户照样铸造凭证，只是不出现在返回值里。** 撤销访问绝不能销毁凭证——重新启用时若发下一个不同的 secret，用户已配置好的每个客户端都会静默失效。`EnsureCredentials` 因此对所有绑定用户调 `PutCredential`（幂等），再用 `Allowed` 过滤出该装到节点上的那批。
- **`StatsEmail` 的唯一性只来自三个 id，绝不来自名字。** 名字可改、释放后可被复用、还扛不住 sanitize：一个纯中文名字过完 sanitize 什么都不剩，只靠名字派生就会把两个用户并到同一个 key 上，静默合并流量——而 `credentials.email` 是 UNIQUE，还会连带把整个节点的装配搞挂。名字只作可读前缀，无可用字符时整个丢掉。
- **key 在铸造时固定**，之后改名不影响已有的流量历史。
- **`sanitize` 存在的两个具体坑**：Xray 用 `>>>` 分隔 stat 名的各字段；`xray api rmu` 把 email 当位置参数吃，所以开头的 `-` 会被解析成 flag，那个用户就永远删不掉了。不合规字符一律丢弃而非替换。
