# alert — 节点可用性通知

扫一遍全部节点的在线状态，把**已经稳定下来**的状态变化推给启用的通知目标（Telegram Bot API / 通用 webhook）。

## 关键决策

- **`Debounce = 2 分钟`**：新状态得先保持这么久才值得告诉人。链路抖动时不去抖就是每个心跳一条消息，而这会**训练人忽略这个频道**——告警失效最常见的方式。
- **从扫描出的状态里播报，而不是在断连那一刻**。这样面板重启不会漏报，去抖也天然有地方待（状态和 `changed_at` 都在库里）。
- **先标记已播报，再投递**。投递失败不会让同一条消息永远排队重试；下一次真实变化照样播报。
- **一个目标失败不影响其他目标**，每个目标的投递结果都记回库，运维在 UI 上能看到。
- **Telegram 的 config 是 `<bot-token>:<chat-id>`，从右边切分**——bot token 本身就含冒号。
- **成败只看状态码，非 2xx 时把响应体前 200 字节拼进错误**——运维在 UI 上看到的就是这段摘要，没有它，「Telegram 拒了」和「网络不通」长得一模一样。反过来说：一个在 HTTP 200 里报失败的 API，这里会当成成功，那段摘要也不会被记下来。
- `Deliver` 导出是为了 API 能提供「发一条测试消息」——这是事故发生前唯一能发现 chat id 写错了的办法。
